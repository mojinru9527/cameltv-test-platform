## 0. 结论速览（TL;DR）

**一句话结论**：平台作为"测试管理平台"（用例库 + 计划 + 报告 + 缺陷 + 追溯）骨架合格、AI 用例生产与接口资产导入真实提效；但作为"自动化执行平台"当前**不可信、不可规模化**——执行引擎存在僵尸任务、长事务、双轨双写、统计口径四分五裂，测试工程师无法用它的执行结果做任何发布决策。四类用例（功能/接口/UI）与计划之间关联松散断裂，899 个接口资产仅 71 条用例（端点级覆盖约 3~4%）、8984 条用例仅 3303 条入计划（36.8%）、三大版本计划通过进度全部为 0。

**用生产数据回答"能不能帮我高效测体育直播"**：

| 能力 | 判定 | 一句话依据 |
|------|------|-----------|
| 接口回归（赛事数据/直播/回放/UGC/广告/银钻接口） | 🟡 可用但不可信 | 899 资产已导入 7 服务，引擎真实；但 71 条用例 359 条失败执行记录（通过率 1.1%），红灯常态化 |
| 需求→用例生产 | 🟢 真实提效 | 1157 条 AI 导入用例、Agent 12 次执行 99% 采纳率、蓝湖 109 页自动采集 |
| 计划编排与执行 | 🔴 阻断效率 | 405/2891/325 三大计划通过进度全 0；批量执行 statement timeout；任务卡"执行中"2 天 |
| UI 自动化 | 🔴 基本跑不起来 | 385 UI 用例仅 10 个任务，4 个 Playground 任务全部"未绑定"环境，2 个任务卡"运行中"2 天 |
| 缺陷/报告/门禁 | 🟡 可用但数字不可信 | 8 缺陷在管、5 报告已生成；但通过率三个口径（9.1%/22.1%/27.1%）并存 |
| 流质量/音视频巡检 | 🔴 不适用 | 路由已隐藏、防盗链流无 Referer/Cookie 支持、HLS 码率指标缺陷（batch-173 复核） |

## 2. 逐模块深度评估

> 判定图例：🟢 保留（真实提效）/ 🟡 保留需修（有价值但有缺陷）/ 🔴 精简或废弃（无数据/阻碍效率）。每个模块按【效率价值】【适配性问题】【冗余判定】【实测证据】四段给出。

### 2.1 用例服务（功能用例）

- **效率价值**：**全平台唯一的主资产库**。8528 条功能用例按 用户端 5067 / 运营后台 3461 组织，CRUD、搜索、导入导出（Excel/XMind）、评审流、版本历史齐全。测试工程师的"用例资产沉淀"需求被满足。脑图（8528 条树状可视化）对 16.0.0 大版本需求梳理真实有用。
- **适配性问题**：
  1. **用例内容质量被 AI 生成损坏**（UI-02）：生产用例正文数字被错误拆分，如「假设上限 2、1 3、0 4、0 5、0 6、」「latestVersion= 2、0」（testcase.txt 第 97、227 行实测）——**可执行性直接受损**，测试工程师拿到这类用例无法照做，必须手工改。搜索"2、0"可复现多行，说明是批量性污染。
  2. **P0 用例占比过高且全部人工可执行性为零**：功能 P0 3206 条（37.6%）+ P1 4560 条（53.5%）。3206 条 P0 靠人工回归在版本周期内不可完成，而当前没有把它们与自动化资产挂钩的通道（见 §4）。
  3. **域体系不统一**（UI-14）：域既有一级体系（用户端/xxx、运营后台/xxx、接口测试/xxx），又有裸域（UGC、广告、赛事、球队、银钻预测、虚拟货币…），trace 按域覆盖列表 100+ 项扁平无分组（UI-06），筛选效率低。
  4. **口径混乱穿透到用例**：功能用例"通过率 9.5%"既不等于按已执行（726/737=98.5%）也不等于按用例总数（726/8528=8.5%），与同表接口 1.1%、自动化 12.5% 的行不可比（见 §3）。
- **冗余判定**：🟢 **保留**（核心资产）。建议：修复用例数字污染（一次性清洗脚本 + 生成 prompt 加"数字禁止加顿号"规则）；域体系收敛为 用户端/运营后台/接口测试 三级。
- **实测证据**：testcase.txt（8528 条、427 页分页、5 项必填校验）、trace.txt 域列表、00-evidence §3 CRUD 全通过（POST 200/搜索/删除 200）。

### 2.2 测试计划

- **效率价值**：计划是"版本验收的容器"，11 个计划覆盖 15.0.0 上线回归（2891 条）、16.0.0 开发验收（405 条）、每日回归（325 条）及批次验证小计划。计划 CRUD、用例编排、环境选择、失败自动转缺陷/报告/通知开关（batch-151）骨架齐全——**这是对的方向**。
- **适配性问题**：
  1. **三大计划通过进度全部为 0**（testplan.txt）：TP-SPORTS-1600 **0/405**、TP-SPORTS-1500 **0/2891**、PLAN-AC9591BA **0/325**——16.0.0 开发验收、15.0.0 上线回归、每日回归三套最重要的计划**从未产出过一条通过记录**。版本质量在计划维度是"零数据"。
  2. **计划编排只覆盖 36.8%**：8984 条用例仅 3303 条唯一入计划（trace.txt），63.2% 用例从未被任何计划引用——用例库与计划两层皮。
  3. **批量执行生产不可用**：`execute-all` 默认同步阻塞（test_plan.py:337），生产库 statement timeout（batch-173 实测 execute-all 直连 Railway code=1、86 用例全 pending；2026-08-13 评测实测 async 路径 10 分钟零进展）。长事务（ARCH-03，`execute_all_cases` 单事务末尾 commit，test_plan_service.py:924-1119）锁行导致单条执行也挂起 >60s。
  4. **计划执行双轨**（ARCH-04）：同一计划 API 执行同时写 `test_execution` 与 `api_execution_task_item`，双向互指 → 统计分裂（§2 矛盾表）。
  5. **任务状态与用例结果矛盾**：任务 tab 显示"计划执行-体育平台-15.0.0-上线回归计划 **0 通过 16 失败 状态:成功**"（15-task-tab.txt）——**任务级"成功"与用例级"全失败"并存**，测试工程师无法据此判断回归结果。
- **冗余判定**：🟢 **保留**（核心），但执行链路必须重建（§5 Top 建议 1-2）。
- **实测证据**：testplan.txt（11 计划全"进行中"、进度明细）、15-task-tab.txt（16 任务含 2 个卡"执行中"、同名任务重跑结果差异）、report-arch-backend.md §3/§6。

### 2.3 执行（计划执行 / 批量任务）

- **效率价值**：执行引擎是"自动化回归"的唯一载体，方向正确；batch-112/113 曾跑出 170 条通过的接口批量任务（15-task-tab.txt），证明引擎在理想状态下能工作。
- **适配性问题**（这是本报告判定"不可信"的核心）：
  1. **僵尸任务**（ARCH-01 用户可见证据）：「重跑-16.0.0-接口回归」「重跑-15.0.0-全量接口回归」两个任务从 2026/8/12 起卡"**执行中**"至少 2 天（0 通过 0 失败）；UI 侧「16.0.0-开发页面验收-UI」「15.0.0-上线核心路径回归-UI」同样卡"**运行中**"自 8/12 13:25 至今（uitest.txt）——根因：APScheduler 轮询与 api_task_worker 守护线程并行认领（task_worker.py:53-62），认领后 `status not in ("pending",)` 守卫直接 return（:82），任务永久 running 且无 stale 回收。**测试工程师看到"执行中"无法区分真在跑还是卡死**。
  2. **同名任务重跑结果不可复现**：batch-112 两次运行 **170 通过/0 失败** vs **161 通过/9 失败**；batch-111 **68/102** vs **0/170**（15-task-tab.txt）——同脚本两次结果天差地别，回归"是否引入新失败"根本无法判定。
  3. **系统性 0 通过模式**：16.0.0 接口回归 0/11、批量执行 0/34、计划执行 15.0.0 0/16 ×2——大批量全失败指向环境/Token/超时/断言配置的系统性问题，而非 34 个真实缺陷；测试工程师必须逐条排查，纯浪费工时。
  4. **历史失败残留污染口径**：接口用例 71 条产生 **359 条失败执行记录**（每条平均重跑 5+ 次仍失败），通过率被历史数据拖到 1.1%——红灯常态化后红灯失效（cry wolf）。
  5. **双 worker 竞态**（ARCH-02 TOCTOU）：PG 下 SELECT→UPDATE 无锁认领，同任务可能被两个 worker 重复执行 → 8024 条执行记录 vs 3303 条已执行用例，重跑记录虚增（dashboard 口径）。
  6. **UI 执行三套入口并存**（ARCH-06：ui_runner_queue + task_worker 轮询 + open_api 裸线程）——调度冗余与重复入队风险。
- **冗余判定**：🟡 **保留但必须重建**——统一任务队列、修僵尸、拆长事务（后端报告 §7 建议 1-3 是测试工程师视角的 P0 前置条件）。
- **实测证据**：15-task-tab.txt（16 任务明细）、uitest.txt（10 任务明细）、00-evidence §2/§6、report-arch-backend.md §3。

### 2.4 接口测试（接口资产 / 接口用例）

- **效率价值**：**全平台自动化价值最高的模块**。899 个接口资产已覆盖 7 个服务（account-service / api-gateway-service / camel-mimo / camel-service / live-platform / payment-service / studio-service），与体育业务高度相关：`/ee/sports_live/football/match/*`（赛事数据）、`/ee/replay/list`（回放）、`/admin/ads/*`（广告）、`/ee/diamond/*`（银钻/钱包）、`/ee/forecast/realtime/odds`（预测赔率）、`/account-service/login/anonymous/web`（匿名登录）等真实端点已在资产库。OpenAPI 导入、快速调试、批量执行、curl 复制、失败分析功能齐全；生产保护（写方法需 `apitest:execute_prod`）设计正确。
- **适配性问题**：
  1. **覆盖缺口巨大**：71 条接口用例仅落在约 30 个端点上——**端点级覆盖率约 3~4%**（71/899=7.9% 是资产级口径，但多数端点仅 1 条用例且 899 资产中绝大多数无任何用例）。96% 的接口资产没有任何自动化用例。**体育直播最核心的赛事数据/直播流接口日常回归实际无人覆盖**。
  2. **已有用例可信度崩坏**：4 通过 / 359 失败执行记录（1.1% 通过率）——测试工程师无法区分"接口真的坏了"还是"用例配置坏了"。
  3. **用例生成能力闲置**：接口用例生成（OpenAPI→用例）已实现（15-apicase-tab 显示各端点 1~14 条用例），但批量生成对 899 资产未规模使用。
  4. **数据驱动链路未闭环**：数据集 4 个已存在（version/module/check 等 2~3 行），但无生产证据显示某接口用例真正用 `${变量}`/dataset_id 跑通多行数据回归——batch-154 打通了能力，使用未验证。
  5. **接口用例与功能用例零关联**（见 §4.2 断裂点 1）。
- **冗余判定**：🟢 **保留**（核心，先修执行可信度，再补 P0 端点用例）。
- **实测证据**：apitest.txt（899 资产 7 服务 45 页）、15-apicase-tab.txt（71 条用例的端点分布）、15-task-tab.txt（任务结果）、report-arch-backend.md §3（执行引擎问题）。

### 2.5 UI 自动化（UI 任务 / Playground / UI 用例）

- **效率价值**：Playwright 真实子进程执行 + 产物（截图/视频/trace）收集，Playground 批量编译（batch-166）把功能用例→spec→UI 任务的链路做出来了——**这是四者关联里唯一一条已实现的自动化通道**，方向完全正确。
- **适配性问题**：
  1. **Playground 回写任务全部"未绑定"环境**（uitest.txt）：4 个 `[Playground]` 任务（横幅广告 10193、开屏广告 10191、中场广告 10200）目标环境列全部"未绑定"、状态"待执行"——**回写创建的任务永远无法执行**。根因（源码）：`playground_service._write_spec_as_ui_job`（:413-440）创建 `UiTestJobCreate` 时**未传 environment_id**（:427-433）。一条本应"编译→执行→回填"的自动化链路断在最后一公里。
  2. **回写无幂等 → 重复任务**（UI-03）：「[Playground] 横幅广告…10193」「[Playground] 开屏广告…10191」各出现 2 条完全重复任务——`_write_spec_as_ui_job` 每次调用无脑新建 UiTestJob，无 (case_id, spec) 查重。重复执行同一回归会无限堆积任务。
  3. **僵尸 UI 任务**：2 个任务卡"运行中"2 天（8/12 13:25 至今）——UI run 状态机 `pending/running/done/fail` 无 stale 回收（后端报告 §3.1）。
  4. **用例↔任务脱节**：385 条 UI 用例（用例服务-UI 自动化）与 10 个 UI 任务之间，仅 4 个 Playground 任务有关联用例（case_id），其余 6 个任务关联用例为空——**用例库的 UI 用例没有系统性转成可执行任务**。
  5. **生产 UI 执行需特权**：`uitest:trigger_prod` 普通成员无权限（2026-08-13 评测 403），但生产 UI 任务 10 个全绑定 PROD 环境，权限与使用场景不匹配，且无权限申请引导。
- **冗余判定**：🟡 **保留（核心）但需三项修复**：① 回写时绑定默认环境（缺省取项目默认/最近使用环境）；② 创建前按 (case_id, spec) 查重或 upsert；③ UI run 增加 stale 回收。修复后这是体育直播 UI 回归（广告轮播、开屏、UGC 列表、订阅付费流程）的唯一可行通道。
- **实测证据**：uitest.txt（10 任务：4 未绑定 + 2 重复 + 2 僵尸 + 1 失败）、playground.txt（批量编译列表）、playground_service.py:413-440（回写无环境无幂等）、report-arch-backend.md §3（三套入口）。

```
TestCase ←── Defect.case_id(无FK)（8 缺陷仅 4 个有值）

执行双轨: test_execution(计划维度) ⇄ api_execution_task_item(任务维度) 双向 api_task_id/test_execution_id 互指
```

### 4.3 优化方案：功能用例 P0 锚点 → 单链路关联模型

**设计目标**：让"一条功能用例"成为可下钻、可执行、可回填、可追溯的质量锚点，四个维度（功能/接口/UI/计划）围绕它形成单链路。

#### 4.3.1 数据模型（建议）

```sql
-- 1) 用例间关联表（新增，替代散落的整数列）
CREATE TABLE case_link (
  id            BIGINT PRIMARY KEY,
  project_id    BIGINT NOT NULL,
  parent_case_id BIGINT NOT NULL REFERENCES test_case(id),  -- 功能用例（锚点）
  child_case_id BIGINT NOT NULL REFERENCES test_case(id),    -- 接口/UI 用例
  link_type     TEXT NOT NULL CHECK (link_type IN ('api','ui','scenario')),  -- api=接口用例 / ui=UI用例
  endpoint_id   BIGINT NULL REFERENCES api_endpoint(id),     -- link_type=api 时绑定端点
  spec_key      TEXT NULL,                                   -- link_type=ui 时绑定 spec 唯一键
  created_by    BIGINT, created_at TIMESTAMP
);
CREATE UNIQUE INDEX uq_case_link ON case_link(parent_case_id, child_case_id, link_type);

-- 2) UI 任务幂等约束（新增唯一索引，替代无脑新建）
CREATE UNIQUE INDEX uq_ui_job_case_spec ON ui_test_job(case_id, test_spec);
-- 并在 UiTestJobCreate 回写链路强制 environment_id 非空（playground_service._write_spec_as_ui_job）

-- 3) 执行记录单一事实源（改造，替代双轨）
-- test_execution 增加 run_type: plan/manual/playground/ci
-- api_execution_task_item / ui_test_run 增加 execution_id FK → test_execution(id)
-- 废弃 ApiExecutionTaskItem.test_execution_id / TestExecution.api_task_id 双向互指
-- 统一状态枚举常量: pending/running/passed/failed/skipped/cancelled（后端报告 §7 建议 4）

-- 4) 统计单一视图（新增，dashboard/trace/report/integration 全读它）
CREATE VIEW v_execution_stats AS
SELECT project_id, plan_id, case_id, case_type, status, executed_at
FROM test_execution JOIN test_plan_case ON ... JOIN test_case ON ...;
```

#### 4.3.2 流程设计（单链路）

```
① 需求文档（source_doc_id）
     │
② 功能用例 F（P0 锚点，生成时强制绑定 requirement_module_id）
     │
     ├─③a 接口用例 A：生成时绑定 api_endpoint_id + service_id
     │        case_link(F, A, 'api', endpoint_id)         ← 生成器自动写
     │        数据集挂载（dataset_id 默认带出）
     │
     └─③b UI 用例 U：Playground 编译 spec → spec_key
              case_link(F, U, 'ui', spec_key)             ← 编译时自动写
              UiTestJob(case_id=F.id, spec_key, environment_id=项目默认环境) ← 幂等 upsert
     │
④ 计划混合编排：AddCasesModal 勾选功能用例 → 自动带出 case_link 的接口/UI 用例
     （计划内按 case_type 分组展示：F/A/U 三色进度）
     │
⑤ 执行：逐用例短事务（每条用例独立 commit，替代 ARCH-03 单长事务）
     UI 任务执行前强制环境预检（复用 C146-1 预检，未绑定环境直接拒绝并提示）
     │
⑥ 回填：执行结果回写 TestCase.last_run_status（唯一口径 passed/failed/skipped）
     功能用例 F 的 last_run_status = 聚合其关联 A/U 的状态（任一失败=F 失败）
     │
⑦ 失败自动链路（batch-151 已有雏形，补齐）：
     失败 → Defect(case_id=F.id) → TestReport → 通知（渠道已配 2 条）
     │
⑧ 追溯下钻（trace 页扩展）：
     F → 关联 A 的 response_snapshot / assertion_results（接口明细）
     F → 关联 U 的 ui_test_run screenshots/video（UI 产物）
     F → plans → executions → defects 全链
```

#### 4.3.3 收益量化（基于生产数据估算）

|------|------|-----------------|

#### 4.3.4 实施顺序（与后端报告 §7 对齐）

1. **先修地基**（P0）：统一任务队列 + 修僵尸/竞态 + 拆长事务（后端报告建议 1-3）——否则单链路跑起来也是假的。

## 7. 结论

**作为测试管理平台**：合格且真实提效。用例库（8984 条）、AI 用例生产（1157 条导入、Agent 99% 采纳率）、接口资产（899/7 服务）、蓝湖证据（109 页自动 OCR）、版本差异分析（2217 缺口）都是生产数据证明有效的资产；"需求→用例→计划→报告→缺陷→追溯"的管理闭环骨架完整，这在同类自建平台里是不错的完成度。batch-165 的"保留"判定在本报告复核后**大部分维持**，且新增了通知渠道 2 条配置、定时任务 4 个、报告 5 份等"从 0 到 1"的使用证据。

**作为自动化执行平台**：当前不合格且不可信。僵尸任务、长事务、双轨双写、统计口径四分五裂，导致：计划批量执行必失败、接口用例 1.1% 通过率红灯常态化、任务状态与用例结果矛盾、三大版本计划 0 通过进度。测试工程师无法用它的执行结果做任何发布决策——这是本次审查最重要的结论。

**作为体育直播的测试平台**：接口回归（赛事/回放/广告/银钻/UGC）开箱可用，需求生产与版本差异分析强适配；但直播流质量巡检不适用、运营后台不可达、UI 自动化断在环境绑定、批量执行不可用——按 §6 ROI 排序修完前 5 项后，"接口回归 + 用例管理 + 版本验收报告"三梯队可先落地，流质量巡检建议作为与业务方共建的定制项。

**最终建议**：把预算与人力集中在 §6 的 1-5 项（执行引擎、统计口径、四者关联、Playground 回写、P0 接口用例），而不是继续堆新功能模块。当前平台的问题不是"功能不够"，而是"已有的功能跑不出一条可信的绿灯"。
