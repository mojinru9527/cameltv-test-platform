## 一、审查范围与方法

本次审查不做清单式巡检，而是以真实使用动线（登录 → 工作台 → 建用例 → 排计划 → 执行 → 查缺陷/报告 → 知识检索）为线索，对 25 个可达页面 + 26 项菜单 + 8 类对话框做了**四层对抗验证**：

1. **文本层**：25 页 Playwright 渲染文本逐行分析布局、层级、文案与信息架构；
2. **DOM 层**：`04-ui-audit.json` 全站按钮可访问性、表格溢出、行高密度审计；
3. **源码层**：router/菜单 seed/MainLayout/工作台/追溯/用例列表/缺陷表/缺口面板/登录表单等关键文件，验证"看到的"与"写出来的"是否一致；
4. **交叉对账**：发现证据总览 `00-evidence-master.md` 两处结论与源码/DOM 证据**冲突**，本报告已据实修正（见 3.6 节），不再沿袭前一轮错误判断。

**审查立场**：只报告可从证据文件与源码可复现的问题；每个发现给出【位置】【问题描述】【影响】【建议】四要素并标注严重度（P0 阻断/误导数据或不可操作；P1 显著损害核心任务可用性；P2 影响效率与一致性；P3 打磨项）。

## 二、逐维度发现

### 维度 1｜信息架构与导航

#### UI-NA-01【P1】菜单名与落地页语义错位：「版本测试任务」→「版本发布包」
- 【位置】侧边栏菜单第 4 项 `menu:versionmission`（seed.py:20，path=`/release-bundles`）；路由 `/version-mission` 仍重定向 `/release-bundles`（router/index.tsx:229）；落地页标题「版本发布包」（release-bundles/index.tsx:157）
- 【问题描述】菜单名「版本测试任务」暗示"围绕版本组织的测试任务清单"，实际落地是"发布包（模块树容器）管理"，两者是不同业务对象。Command Palette 与访客目录（guestModuleCatalog.ts:43）同样沿用「版本测试任务」名，但页面内容、描述（"管理蓝湖原型版本对应的发布包，构建「项目球」模块树知识图谱"）全是发布包语义。旧路由 `/version-mission` 的重定向进一步坐实了命名迁移未完成。
- 【影响】用户按"任务"预期进入页面，看到的却是发布包/模块树，第一屏即产生"我是不是走错了"的认知摩擦；菜单名与面包屑/页面标题三处不一致，降低导航可信度。
- 【建议】统一为「版本发布包」或「发布包管理」；删除 `/version-mission` 遗留重定向；Command Palette、访客目录、guestModuleCatalog 同步改名。

#### UI-NA-02【P2】同一平台三套命名体系并存
- 【位置】侧边栏 vs Command Palette vs 页面标题：侧边栏「需求文档」/ Palette「需求管理」（CommandPalette.tsx:46）/ 页面「需求文档」；侧边栏「接口测试」/ Palette「API 测试」（:61）/ 页面「接口测试」；侧边栏「运维发布控制」/ Palette「运维发布记录」（:68）；「目标环境」菜单 vs 页面标题「环境与变量管理」（environment 页）；「UI 自动化」菜单 vs 页面标题「UI 测试」（uitest 页）
- 【问题描述】同一入口在侧边栏、Ctrl+K 命令面板、页面标题三处使用不同名称，且 Palette 未收录 DSH 任务、蓝湖证据包两个新菜单（batch-172/173 新增后未同步注册表，CommandPalette.tsx:42-69 无这两项）。
- 【影响】键盘流用户（Ctrl+K）与鼠标流用户看到的是两套地图；新增模块在命令面板里"消失"，违背"全站可搜索"的认知。
- 【建议】建立单一菜单名词典（如 `src/lib/navigation-labels.ts`），侧边栏/Palette/文档标题/breadcrumb 同源消费；Palette 补齐 DSH 任务、蓝湖证据包。

#### UI-NA-03【P2】「系统管理」被排进导航中间，且侧边栏「系统」分组是死代码
- 【位置】seed.py:38 `menu:system` sort=14，夹在「报告中心」(13) 与「我的项目」(15) 之间；MainLayout.tsx:280-286 的分组过滤 `['system','settings'].includes(m.code?.toLowerCase())` 对 `menu:system` 永不命中
- 【问题描述】所有菜单 code 都是 `menu:*` 前缀，MainLayout 的"系统"分组过滤条件永远为空 → 「系统」分组（SidebarGroupLabel 系统）实际从不渲染；同时「系统管理」作为一个设置类页面被平铺在 22 个业务菜单中间，与"知识"独立成组的设计意图自相矛盾。
- 【影响】设置类入口淹没在业务导航中；侧边栏保留了一个永远不出现的"系统"分组逻辑，后续维护者会继续向该分组塞菜单然后发现不生效。
- 【建议】分组过滤改为 `code?.startsWith('menu:system')`；把系统管理（连同我的项目）归入独立分组或置于导航末尾；删除死分组逻辑或改为按业务域分组。

#### UI-NA-04【P2】22 项顶级菜单全部平铺无次级分组
- 【位置】侧边栏「导航菜单」分组内 22 个一级项（工作台/质量追溯/需求文档/版本测试任务/用例脑图/用例服务/测试计划/接口测试/UI 自动化/Playground/定时任务/报告中心/系统管理/我的项目/缺陷管理/测试数据集/集成配置/通知配置/目标环境/Agent 工作台/DSH 任务/蓝湖证据包），证据：workbench.txt:11-32
- 【问题描述】26 项菜单只有"知识"独立成组，其余 22 项在单一滚动列表中。Playground（调试工具）、DSH 任务（运维型）、蓝湖证据包（采集型）、定时任务（调度型）与业务核心（用例/计划/缺陷）同级平铺；且 `menu:uitest` 与 `menu:playground` 的 sort 同为 10（seed.py:32-33），排序无主次。
- 【影响】导航深度扁平到极限，用户依赖记忆定位；菜单随模块增长线性膨胀（batch-172 加 DSH 任务、batch-173 加蓝湖证据包），无分组缓冲。
- 【建议】按「质量核心（工作台/追溯/用例/计划/缺陷/报告）」「专项测试（接口/UI/Playground）」「自动化运维（定时/DSH/蓝湖/发布包）」「配置（环境/数据集/集成/通知/系统/项目）」4 组分组；或至少为 Playground/DSH/蓝湖增加分组标题。

#### UI-NA-05【P1】生产环境存在多个"可点但必失败/必空"的入口
- 【位置】① 侧边栏「DSH 任务」：页面显示「DSH 服务未启用」横幅，但「新建任务」按钮照常可点（dsh-tasks.txt:46-47，UI-11）；② 「主题实验室」菜单 → 生产点击进入「主题实验室未开放」占位页（theme-lab.txt:42-44，`VITE_ENABLE_THEME_LAB` 未开）；③ 「运维发布控制」整页「未启用发布控制数据源」占位，仅一个"刷新记录"按钮（operations-release.txt:44-61，UI-12）；④ Agent 工作台「DSH 执行」卡显示「暂不可用」（agent-workbench.txt:86），与 DSH 任务页的表达又不同
- 【问题描述】四个入口在功能不可用时选择了"展示但不可用"而非"隐藏或禁用"。其中 DSH 任务页最危险：用户能输入任务、点提交，然后必然失败。
- 【影响】三种失败模式（横幅+可用按钮 / 占位页 / 整页空壳）给用户三种不同的"坏掉"信号；对不可用功能的反复点击消耗信任。
- 【建议】不可用时统一策略：菜单项禁用+tooltip 说明、或整页用一致的"未配置 + 配置引导"模板；DSH 任务页在服务未启用时禁用新建按钮并给出配置指引链接；主题实验室在生产从菜单隐藏。

#### UI-NA-06【P3】内部批次号/工单号泄漏到用户界面
- 【位置】需求页面板标题「交互覆盖缺口（C119-2）」「生产差异标注（C102-4）」（requirement.txt:110,116）；Playground 页描述「回写 UI 任务（batch-166）」（playground.txt:44）；环境下拉项「体育平台生产只读接入（Batch 101）」（environment.txt:54）
- 【问题描述】用户可见文案直接内嵌开发批次/工单编号，像把 Jira ticket 名贴在功能名称上。
- 【影响】非技术用户看到"（C119-2）"无法理解；界面显得是内部工具而非产品。
- 【建议】从用户文案剥离批次号，改为业务化副标题；如需追溯在详情/关于页保留。

### 维度 2｜视觉一致性

#### UI-VC-01【P2】缺陷严重度标签双风格：「P0 致命」vs「P0-致命」
- 【位置】缺陷页统计卡 label「P0 致命」（DefectStatsCards.tsx:25，空格分隔）vs 行内徽标「P0-致命 / P1-严重 / P2-一般 / P3-建议」（constants.ts:7-10，连字符分隔）；同一行统计卡「P0 致命」与下方表格「P0-致命」指向同一概念（UI-13）
- 【问题描述】同一语义两种排版；且四级严重度用"致命/严重/一般/建议"中文词 + 编号混合表达，与用例页优先级纯「P0/P1/P2/P3」徽标、追溯页「P0 缺陷/P1 缺陷/P2 缺陷」图例（report.txt:71）又是另一套。
- 【影响】跨页面读取同一字段需反复解码；设计系统缺一个"严重度"单一规范。
- 【建议】统一为 `P0 · 致命` 或 `P0-致命` 一种格式，并在设计 token 层定义 Severity 组件（颜色+文案+语义）全局复用。

#### UI-VC-02【P2】缺陷统计卡一行混排两个统计维度
- 【位置】DefectStatsCards.tsx:17-43：四卡 = 缺陷总数（总量） / P0 致命（严重度维度） / 待处理（状态维度） / 已解决（状态维度）
- 【问题描述】同一行卡片序列中，"P0 致命"取严重度口径，另两张取状态口径，视觉上像四个并列状态。实测数字：总数 8、P0 3、待处理 7、已解决 1 —— 3+7+1≠8，用户无法对账（缺陷总数与状态/严重度两套切片的和天然不等，但卡片并排暗示可加和）。
- 【影响】统计卡被误读为状态分布；"待处理 7"与列表"已关闭 1 + 待处理 7 = 8"能对上，但"P0 致命 3"插在中间破坏了可加性直觉。
- 【建议】改为两行（一行严重度分布 P0-P3、一行状态分布），或明确分组标题「按严重度」「按状态」。

#### UI-VC-03【P3】状态术语不统一：「已解决」卡 vs「已关闭」行
- 【位置】DefectStatsCards.tsx:40 `(by_status.resolved||0)+(by_status.closed||0)` 标「已解决」；列表/详情徽标来自 STATUS_MAP（constants.ts:13-20）只有 `closed: '已关闭'`，无 `resolved` 键
- 【问题描述】统计卡「已解决 1」对应的行显示「已关闭」；STATUS_MAP 定义的六态（待处理/已确认/修复中/待回归/已关闭/已拒绝）与详情抽屉状态切换可选项一致，但统计卡用了不在状态机里的词"已解决"。
- 【影响】用户在同一页面看到"已解决"和"已关闭"以为是两种状态。
- 【建议】统计卡直接引用 STATUS_MAP 文案，删除 `resolved` 残留分支。

#### UI-VC-04【P2】追溯漏斗六节点量纲不一、阶段标签错位
- 【位置】trace.txt:65-88 漏斗：01 需求 6 已覆盖 / 02 用例 8984 已就绪 / 03 计划 3303 已编排 / 04 执行 3303 **执行中** / 05 缺陷 4 有缺陷 / 06 报告 **22.1%** 关注
- 【问题描述】前五节点是数量（6/8984/3303/3303/4），末节点是百分比（22.1%）；"04 执行 3303"的阶段说明写「执行中」——3303 是"已执行"的累计数，标签却是进行时态。且"03 计划 3303 已编排"与"04 执行 3303"数字相同，两个阶段无区分度。
- 【影响】漏斗（funnel）本意是逐级收窄，但"计划 3303 → 执行 3303"毫无收窄（覆盖率 36.8% 的收窄发生在 02→03 之间），"报告 22.1%"把通过率混入数量序列，层级叙事被打断。
- 【建议】末节点改为"报告 5 份"或"通过率 22.1%"单独标注；阶段说明改为"已执行"；03/04 若数据相同应合并或说明"计划即执行"。

#### UI-VC-05【P2】用例域命名体系混排（追溯「按域覆盖」实锤）
- 【位置】trace.txt:108-321「按域覆盖」100+ 域：`用户端/xxx`、`运营后台/xxx`、`运营后台-热门比赛配置`（连字符变体）、`接口测试/xxx`、`接口测试`（裸域）、`UGC`、`广告`、`WEB-第三方社媒引导移除`（英文前缀）、`体育数据-篮球`、`篮球相关-广告调整`、`通知-比分变更`、`APP-版本更新`（UI-14）
- 【问题描述】同一层级里至少 5 种命名范式共存："平台前缀+斜杠"、"平台前缀+连字符"、"裸模块名"、"专题连字符"、"英文前缀"。用例新建对话框的「所属域」下拉（05-case-dialog.txt）把这三类 100+ 项全部扁平混排（`用户端`、`运营后台`、`接口测试` 三个平台名之后直接跟 `APP-版本更新`、`UGC`、`UGC内容`……），用户无法预测某个模块会以哪种形态出现在列表。
- 【影响】域既是新建用例的必填字段、又是追溯/脑图的聚合维度，命名混乱直接放大表单选择成本与统计归类的不可信感。
- 【建议】数据迁移归一（`运营后台-` → `运营后台/`），平台前缀一律斜杠；裸域补前缀；UI 侧按 用户端/运营后台/接口测试/其他 分组渲染，并提供搜索（见 UI-FM-01）。

#### UI-VC-06【P3】同一用例类型三种叫法
- 【位置】用例对话框「UI 用例」（05-case-dialog.txt）；用例页 tab「UI 自动化 (385)」（testcase.txt:48）；工作台图表「自动化用例」（workbench.txt:102）——对应接口类也有「接口用例」「API 用例」（workbench.txt:54 卡 label 与 55 注）
- 【问题描述】功能用例类型在对话框/列表页/工作台三处叫三个名字。
- 【建议】全站统一「功能用例 / 接口用例 / UI 用例」并做术语表。

#### UI-VC-07【P3】报告中心「模板」列 5 份全为「—」且无默认模板引导
- 【位置】report.txt:87-100 五份报告模板列全部「—」；生成报告对话框提供「报告模板 (可选) 选择模板（留空使用默认）」（19-report-dialog.txt:19-21，UI-09）
- 【问题描述】对话框说"留空使用默认"，但列表对"默认模板"零呈现；五份报告全部为空模板，等于默认模板从未生效或被静默跳过。
- 【影响】"模板"功能在列表层完全不可见，用户不知道默认模板存在与否。
- 【建议】列表对默认模板显示「默认」徽标；若生成时未选模板则在详情中标注"默认模板"。

#### UI-VC-08【P3】工作台两种主题的指标卡结构不一致
- 【位置】workbench/index.tsx:153-158（黑曜主题 4 卡：用例总数/API 用例/测试计划/通过率，均带 note）vs :179-188（默认主题 4 卡：用例总数/测试计划/通过率/接口用例）；黑曜主题下「用例总数」卡 note 又是「通过率 9.1%」（workbench.txt:52-53），与独立通过率卡重复
- 【问题描述】同一指标集在不同主题下卡片顺序、标签（接口用例 vs API 用例）、信息层级（带 note vs 不带）都不同；且"通过率"信息在同一屏出现两次。
- 【建议】主题只换皮肤不换信息结构；指标卡收敛为单一组件配置。

### 维度 3｜表格设计

#### UI-TB-01【P1】用例表格 10 列高密度全文直出，核心语义被单行截断
- 【位置】testcase/index.tsx:637-714：10 列（勾选+9 内容列），`min-w-[900px]`；前置条件 180px / 操作步骤 200px / 预期结果 200px，全部 `truncate` + `line-clamp-1` + `text-xs`，且步骤项以 `formatStepActions(...).join(' ')` 拼成一行（:705）
- 【问题描述】列表层同时存在两个相反的问题：横向要容纳 10 列（900px 起），纵向每格只有一行 12px 文字。一屏 20 行 × 9 列全是"被压扁的摘要"，步骤"1、启动 APP…2、确认弹出更新提示 3、点击「立即更新」"在 200px 内只剩 1 行省略号（testcase.txt 的完整文本是 innerText 提取，视觉上并非如此）。要判断一条用例内容必须逐个点开抽屉，批量扫读完全不可行。DOM 审计 `hasEmpty: true`（勾选列）也确认列数膨胀。

- 【影响】**这是对 UI 可信度最致命的问题**：用户无法判断哪个数字是真的，任何决策（是否发布、是否回归）都失去依据；统计展示得再漂亮，口径分裂让整页图表归零。
- 【建议】后端统一口径（用例维度为准，执行记录维度单独标注"含重跑"）；前端各页消费同一 `/dashboard/stats` 派生视图并标注口径说明（tooltip"通过率=已通过用例/已执行用例"）；UI 上对三处数字做一致性断言测试。

### 维度 8｜可访问性

#### UI-AX-01【P1】全站 34 处无文本/无 aria 按钮（缺陷 16 / 报告 10 / 通知 8）+ 知识页 1 处
- 【位置】04-ui-audit.json（/defect:224-286、/report:132-172、/notify:320-350、/knowledge:430-434）（UI-01）
- 【问题描述】见 TB-03 详情；独立成维度是因为其影响面横跨四个页面：删除（danger 变体）、ghost 图标按钮全部无可访问名。`data-variant="danger"` 的 alert-dialog-trigger 是破坏性操作，却对辅助技术完全隐形——这是最需优先处理的 a11y 欠账。
- 【影响】WCAG 2.1 4.1.2 Name/Value 失败；屏幕阅读器用户无法执行删除/编辑；自动化审计持续报红。

#### UI-AX-02【P2】同设计系统内 a11y 双标准
- 【位置】对照 testcase/index.tsx（全部 aria-label）、release-bundles/index.tsx:353 `aria-label={`删除发布包 ${bundle.name}`}`、defect/report/notify（无）
- 【问题描述】四个模块做对了、三个模块没做，说明不是能力问题而是覆盖不全——a11y 实践未形成组件层约束。
- 【建议】在 Button 组件层强制：无 children 文本时必须要求 aria-label（TypeScript 或 lint 规则）。

#### UI-AX-03【P2】长列表无区域语义与虚拟化，键盘导航成本高
- 【位置】trace「按域覆盖」100+ 个 div 卡片（无 landmark/label）；requirement 缺口 45 页列表（ul 无 aria-label）；testcase 表格有 `aria-label="测试用例数据表"` + tabIndex=0（✅ 对比）
- 【问题描述】域覆盖卡片区无 role/region 与 label，屏幕阅读器用户无法"跳到此模块"；缺口 ul 无 accessible name。
- 【建议】给长列表容器加 `role="region"` + aria-label（对齐 testcase 表格的做法）。

#### UI-AX-04【P3】关键信息大量使用 `text-xs text-muted-foreground`（对比度风险，本轮未量化）
- 【位置】全站：表格 note、缺口条目 `text-[11px]`（InteractionGapPanel.tsx:168）、统计卡 note（workbench obsidianMetrics note）
- 【问题描述】04-ui-audit.json 未采集颜色对比度数据，无法断言具体失败项；但"11px 灰字承载缺口信息、12px muted 承载表注"是高对比度风险模式（深色主题下 muted 常低于 4.5:1），且缺口列表的 URL 信息恰恰是 11px。
- 【建议】补一轮 axe-core 对比度自动化（pr-check.yml 已有 a11y 观察位）；对 info 类文本统一 `text-muted-foreground` 的明度 token，保证 ≥4.5:1。

#### UI-AX-05【P3】图表可访问性有基础但覆盖不全
- 【位置】工作台趋势图有 `sr-only` 数据表（workbench/index.tsx:627-629 ✅）、ChartFrame「查看图表数据」✅；但 trace 域覆盖 100+ 卡片无 sr-only 摘要、report 缺陷收敛图（P0/P1/P2 图例）无数据表

## 三、对前轮（batch-127 及证据总览）两处结论的对抗性修正

作为对抗审查，发现证据总览 `00-evidence-master.md` 的两处 UI 结论与源码/DOM 证据冲突，特此修正，避免下游继续引用错误结论：

1. **「需求页交互缺口 2217 条全量平铺无分页」（UI-05）不成立**：`InteractionGapPanel.tsx:87-88,176-198` 明确存在 `GAP_PAGE_SIZE=50` 的分页（45 页，带"上一页/下一页/第 x/45 页"）。requirement.txt 之所以只见 50 条左右即截断，是文本快照上限所致。**真实问题**是弱分页（无跳页）、URL 未解码、首页占满第一页（见 UI-DT-04）——已按真实情况改写。

这两处修正本身即是本报告最有价值的产出之一：UI 审查不能只看文本层，必须 DOM 审计 + 源码交叉验证。

## 六、结论：平台 UI 整体设计水平评价

**基础盘良好，信任盘失守**。这是对本平台 UI 最凝练的评价。

**做得扎实的部分**（值得肯定，非吹捧）：组件体系（radix 系 ui/* 全套）、焦点管理（skip-link、路由切换 focus main-content）、表单 label 与 aria-invalid 全链路（登录/用例对话框）、空态与错误态覆盖率（用例/缺陷/邀请码均有"空态+动作"）、图表 sr-only 数据表先例、用例页行内按钮 aria-label 规范——这些说明团队有真实的设计系统意识和 a11y 基本功，batch-127 那种"纯清单式"审查完全没摸到这些底子。

**但四类问题把整体拉回及格线以下**：

1. **口径分裂（DT-01）是设计层面的失败而非 bug**：三个页面三个通过率，等于设计师把"数字的可信度"这个最底层的信息架构问题让位给了后端双轨表。UI 做得再精致，用户第一眼看到的 9.1% 与 22.1% 就会让他关掉页面。这是 P0 里唯一"修 UI 修不好、必须后端先治理"的问题。
2. **内容质量直接砸在渲染层（TB-02）**：`2、1 3、0 4、0 5、0 6、` 这样的前置条件说明 AI 生成链路与显示启发式在互相放大错误。对一个"用例库"产品，用例正文不可读是产品本体受损。
3. **一致性债务集中在三类**：命名（三套菜单名、三种用例类型叫法、五种域命名范式）、状态（已解决/已关闭/已确认）、严重度标签（P0 致命 vs P0-致命）。这些不是能力问题，是缺少一个"术语与格式单一事实源"。
4. **长列表/大数据展示策略保守**：域覆盖 100+ 卡片平铺、缺口 45 页弱分页、Playground 100 行直出、Agent 历史 400 字符 URL 直出——平台在"数据量大"的场景统一选择了"全量塞给用户"，与用例表 20 行/页的精细分页形成鲜明反差。

**一个观察**：本平台的 UI 质量分布呈"核心工具页（用例/缺陷/报告）最弱、工具型页（知识/接口资产/发布包）反而较强"的倒挂——最该打磨的高频路径恰恰是缺陷最多的路径（用例列表的数字拆分、缺陷行的裸图标删除、报告模板的静默缺失）。建议下一轮 UI 迭代按"高频动线优先"而非"新模块优先"排布资源。

**评分**：整体 5.8/10。具备合格企业级中后台的骨架与审美，但统计可信度（P0）与内容正确性（P0）两条腿都瘸着，任何一位把"数字当真"的测试负责人都会在使用第一周后对平台数据产生系统性不信任——这是本报告认为最需要优先于一切新功能修复的问题。
