### 7.1 Temporal 执行栈（本轮已拉起）
Docker 停着 `aitde-temporal`(server) + `aitde-temporal-pg`(PG)。用户启动 Docker 后：
- ✅ `docker start aitde-temporal-pg` → PG healthy（崩溃恢复）；
- ✅ `aitde-temporal`(temporalio/auto-setup:1.25.2) **Up(healthy)**，map `127.0.0.1:7233`；
- ✅ `.env` 设 `TEMPORAL_ENABLED=true`；`python -m app.modules.aitde.workflow.gateway` **worker 运行/polling** `worker-test` 队列；
- 网关提供 `start_scenario_execution(workflow_id, run_id, scenario_input, task_queue)` 作为 Run→Temporal 分派入口。

> 实现 Run→FINISHED 需要：给场景构建**干净可执行的 command plan**（当前 LLM 场景为 P2 + DB 型 oracle，
> target 是需求文本，无法干净驱动）+ **适配器/驱动**真实执行。要得到干净 P0/P1 PASS，需用
> **OpenAPI source**（后端的 `/openapi.json`）生成含 API oracle 的契约/场景。这是后续构建点。

### 7.2 干净 API 场景的生成尝试（结论）
新起 mission 3 + **OPENAPI source**（指向后端 `/openapi.json` 的 auth 端点）+ 解析(fragment=1) →
scope 评审/完成 → 契约(FROZEN) → 场景生成：**LLM 仍生成 P2 + `DB` 型 oracle**（target 为
Source URI 文本），而非干净 `API` oracle。共同结论：**要让 LLM 生成可干净执行的 API 场景与
command plan，需输入**完整的 OpenAPI 端点/schema 结构 + 明确的契约/oracle 约束**，当前摘要级
输入不足以触发正确 oracle 类型。这属于后续构建点，需更精细的契约建模。

> 已确认能力（无需再验证）：DeepSeek 模型真实可用、AI 全链路生成真实跑通、Temporal 常规栈
> (server+worker) 已拉起并可执行 workflow。**剩余「干净 P0 API 场景 + command plan + API 驱动
> 真实 3 连跑」是**契约/场景建模**层面的构建任务，而非运行时可用性问题。

- **已落地并留档**：覆盖率阈值（74% ≥ 70%）、四层回归基线（2143 过 / 7 基础设施失败）、
  a11y 关键页全绿、迁移单头/结构/b181 修复。

  （≥100 分类 / Golden / Cutover 指标）、完整增量库回滚。

  场景执行等**非只读**操作触碰生产违反 AITDE 硬不变量「Production 默认只读」，需**先确认
  安全边界 + 提供生产访问**，不可盲目执行。
