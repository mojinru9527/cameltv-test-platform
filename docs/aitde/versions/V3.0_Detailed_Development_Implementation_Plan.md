# 0. V3.0 一句话目标

V3.0 不解决“AI 怎么自动执行所有测试”。

V3.0 只解决最重要的第一层问题：

> **AI 到底应该测什么、什么结果才算正确，并把这个结果变成一个可冻结、可追溯、可生成统一 Scenario 的正式测试模型。**

本版本最终打通：

```text
创建 Mission
    ↓
导入 / 关联 Source
    ↓
AI 分析 Scope
    ↓
Tester Review Scope
    ↓
AI 发现 Ambiguity / 生成 Intent
    ↓
Tester 解决关键歧义
    ↓
AI 生成 Contract Draft
    ↓
Tester Review
    ↓
Freeze Contract
    ↓
AI 生成 Scenario + Oracle
    ↓
Tester Review Scenario
    ↓
Functional View
```

V3.0 完成后，测试工程师已经可以在需求评审阶段完成：

- 版本测试范围确认；
- 需求遗漏 / 歧义发现；
- 验收标准确认；
- 测试契约冻结；
- 业务 Scenario 建模；
- Oracle 来源追踪；
- 功能测试用例视图生成。

# 3. V3.0 架构决策

## ADR-001：新建 Mission Aggregate，不继续无限扩展 VersionMission

新增正式领域：

```text
Mission
```

旧：

```text
VersionMission
```

变成 Legacy / Compatibility Source。

原因：

1. Mission 不一定永远等于版本；
2. 未来需要 FEATURE / HOTFIX / REGRESSION / EXPLORATORY；
3. Scope / Contract / Scenario 有独立生命周期；
4. 避免 `VersionMission` 继续堆 URL、scope JSON、执行状态等杂项。

---

## ADR-002：V3.0 引入新 `/api/v2`

现有 `/api/v1` 保持兼容。

新 AITDE Domain 全部：

```text
/api/v2
```

不要把新 Contract / Scenario API 塞进旧 `version_mission.py`。

---

## ADR-003：新领域采用“模块化 bounded-context”，Legacy 不搬家

新增：

```text
backend/app/modules/aitde/
```

但不在 V3.0 搬迁旧 `models/`、`services/`。

目标：

```text
app/modules/aitde/
├ mission/
├ sources/
├ scope/
├ contract/
├ scenario/
├ intelligence/
└ common/
```

这样新代码从第一天保持清晰，同时不制造一次性大规模移动文件风险。

---

## ADR-004：Contract / Scenario 使用不可变版本

身份和版本分离：

```text
TestContract
  └ TestContractVersion

TestScenario
  └ TestScenarioVersion
```

冻结以后：

```text
UPDATE frozen version
```

必须失败。

任何修改：

```text
ChangeProposal
→ New Version
```

---

## ADR-005：AI 只输出结构化候选结果

所有正式 AI 输出：

```text
Pydantic Schema
```

禁止：

```text
LLM markdown
→ regex parse
→ 直接写业务表
```

---

## ADR-006：AI 不能创建无来源的“事实 Oracle”

Oracle 来源必须是：

```text
TESTER_APPROVED
REQUIREMENT_EXPLICIT
API_CONTRACT
BUSINESS_RULE_SOURCE
DB_CONSTRAINT
APPROVED_BASELINE
AI_INFERRED
```

其中：

```text
AI_INFERRED
```

默认：

```text
required = false
review_status = PROPOSED
```

只有 Tester 批准后，才能成为 Required Oracle。

# 5. 数据库 Migration 总览

V3.0 建议拆成 4 个 Alembic Revision，不要一个 migration 创建所有表。

```text
M1: mission + source foundation
M2: scope + ambiguity + intent
M3: contract + scenario + oracle
M4: legacy backfill + compatibility
```

命令原则：

```bash
cd test-platform-v2/backend

alembic revision --autogenerate -m "v3 mission and source foundation"
alembic revision --autogenerate -m "v3 scope ambiguity intent"
alembic revision --autogenerate -m "v3 contract scenario oracle"
alembic revision -m "v3 legacy version mission backfill"
```

实际 revision id 以当前 Alembic head 为准，不在文档中硬编码。

# 9. Migration M4：Legacy Backfill

## 9.1 VersionMission → Mission

脚本：

```text
backend/scripts/migrate_version_missions_to_v3.py
```

映射：

```text
VersionMission.project_id
→ Mission.project_id

mission_key
→ mission_key

title
→ title

version
→ version_label

qa_owner_id
→ qa_owner_id

created_by
→ created_by

environment_id
→ default_environment_id

VersionMission.id
→ legacy_version_mission_id
```

状态映射必须保守：

```text
旧 draft
→ DRAFT

旧数据存在 requirement / api source
但没有人工 V3 Review
→ SOURCE_READY

禁止迁移时自动标：
CONTRACT_FROZEN
SCENARIO_READY
ACCEPTED
```

---

## 9.2 Requirement 关联

如果：

```text
requirement_doc_id != null
```

创建：

```text
SourceArtifact(provider="legacy_requirement_doc")
MissionSourceLink(role="REQUIREMENT")
```

SourceArtifact 不重复复制原文件二进制，先保存：

```text
provider_ref:
{
  "legacy_requirement_doc_id": ...
}
```

并生成 normalized snapshot。

## 9.3 requirement_url / api_spec_url

如果存在：

```text
requirement_url
api_spec_url
```

创建对应：

```text
SourceArtifact
```

但：

```text
parse_status = PENDING
```

迁移脚本不能偷偷请求外网或内网。

## 9.4 TestCase

V3.0 **不批量把历史 TestCase 自动转换成正式 Scenario**。

原因：

- 旧 Expected 可能不完整；
- 旧 Case 可能重复；
- AI 反向生成会制造“看似结构化但未经确认”的新事实。

V3.0 只做：

```text
Legacy Case Reference
```

Scenario 页面未来可以：

```text
关联历史用例
```

正式迁移历史 Case 放后续专项。

# 41. Prompt 1：`scope_analysis_v1`

目标：

> 只判断“应该测什么”，不生成测试用例。

硬规则：

```text
1. 不得生成 TestCase。
2. 每个 Scope Item 必须带 source_refs。
3. 缺少证据时必须标低 confidence。
4. 不得把 AI 猜测写成 REQUIREMENT_EXPLICIT。
5. 必须区分 INCLUDE / EXCLUDE。
6. 必须给 test_depth。
7. 识别关联回归区域，但必须说明 reason。
8. 不得使用 Git 作为必需输入。
```

输入：

```text
mission metadata
normalized source fragments
existing requirement modules（可选）
OpenAPI summary（可选）
historical risk summary（V3.0 可为空）
```

输出：

```text
ScopeAnalysisOutput
```

---

# 42. Prompt 2：`ambiguity_intent_v1`

目标：

```text
发现“需求没有讲清楚的地方”
+
提炼 Test Intent
```

硬规则：

```text
1. 不替 Tester 选择业务规则。
2. Source 冲突必须创建 Ambiguity。
3. 需求未覆盖但 API/数据模型出现的新状态 → Ambiguity。
4. Intent 不描述 locator / HTTP / SQL。
5. Intent 只描述 business goal / required outcomes。
```

---

# 43. Prompt 3：`contract_builder_v1`

目标：

> 把已确认 Scope + 已解决 Ambiguity + Intent 变成 Contract Draft。

硬规则：

```text
1. 不创建未有来源的 Required Business Rule。
2. AI_INFERRED 必须显式标识。
3. 不允许把当前系统行为当需求标准，除非 Tester Approved。
4. 不生成 Playwright/API 请求。
5. 每个 required outcome 都必须可转换成 Oracle。
```

---

# 44. Prompt 4：`scenario_design_v1`

目标：

> 从 Frozen Contract 生成业务 Scenario。

必须继承当前 `test-case-design` 的测试专业规则：

```text
负面
边界

异常
端差异（按需）
```

但输出不再是传统三套 Case，而是：

```text

```

硬规则：

```text
1. Scenario 必须绑定 Frozen Contract Version。
2. 不能新增与 Contract 冲突的 Expected。
3. Oracle 必须引用 Contract Rule / Source。
4. UI/API/DB 只作为 Oracle type，不生成执行代码。
5. 同一业务意图优先形成 Scenario，不按 manual/api/ui 重复三份。
```

# 120. 最终开工结论

V3.0 的重点不是把 AI 做得“更自动”。

它要先把现有平台最关键的测试设计链，从：

```text
Requirement
→ AI
→ TestCase
```

升级成：

```text
Source
→ Scope
→ Ambiguity
→ Intent
→ Human Review
→ Frozen Contract
→ Scenario
→ Oracle
→ Functional Projection
```

其中：

- `Source` 解决“依据是什么”；
- `Scope` 解决“这个版本测什么”；
- `Ambiguity` 解决“需求哪里没讲清”；
- `Intent` 解决“我们到底想证明什么”；
- `Frozen Contract` 解决“什么才算正确”；
- `Scenario` 解决“统一测试事实模型”；
- `Oracle` 解决“预期怎么追溯”；
- `Functional Projection` 保证现有测试工程师仍然可以用熟悉的功能用例方式工作。

**只有这一层稳定以后，V3.1 的 Replay、V3.2 的造数据、V3.3 的 UI Hybrid、V3.5 的 RED → GREEN 才不会把错误的测试理解自动化。**
