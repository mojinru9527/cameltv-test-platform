## Part A — 准备数据源（V32-001/004）

**UI**：`/data-sources`；**API**：`/api/v2/data-sources`

1. 创建一个**只读/读写数据源**（用于 DB/API 数据），如：
   ```http
   POST /api/v2/data-sources
   { "source_type": "POSTGRES", "name": "验证订单库", "environment_id": <环境id>,
     "access_mode": "READWRITE", "secret_ref": "sec/pg", "config": { "host": "127.0.0.1", "port": 5432, "database": "tp", "table_allowlist": ["membership", "user"] } }
   ```
   `config` 内**禁含** `password/secret/token` 等敏感键（后端拒绝并提示改用 `secret_ref`）。
2. `GET /api/v2/data-sources` → 列表；确认返回字段为 `config_json`（字符串），前端已解析为对象。
3. `POST /api/v2/data-sources/{id}/test` → 返回 `{ok, latency_ms, detail, secret_leaked:false}`；`detail` 为类别文案（`unavailable:*` / `ok`），**不含凭据**。

> ✅ 成功标准：UI 列表渲染；新建后即时出现；「测试连接」徽章显示 已连接 + 延迟；`secret_leaked=false`。

## Part B — 构建 Mission 链（拿到 `scenario_version_id`）

> 目的：获得一个带 `given/expected` 业务状态的场景版本。UI 可在 `/missions` 完成；此处仅列关键 API。

1. 建任务：`POST /api/v2/missions` `{ "title": "V3.2 数据验证", "mission_type": "VERSION", "version_label": "1.0.0" }` → `mission_id`
2. 挂需求/接口来源：`POST /api/v2/missions/{mission_id}/sources`（`source_type=REQUIREMENT|OPENAPI`，附内容/URL）
3. 范围分析：`POST /api/v2/missions/{mission_id}/scope/analyze`，再 `POST /api/v2/missions/{mission_id}/scope/complete`
4. 生成合同：`POST /api/v2/missions/{mission_id}/contracts/generate` → `contract_id`
5. 冻结合同：`POST /api/v2/contracts/{contract_id}/freeze`（状态须为 `FROZEN`）
6. 生成场景：`POST /api/v2/contracts/{contract_id}/scenarios/generate`
7. 取场景与版本：
   - `GET /api/v2/missions/{mission_id}/scenarios` → `scenario_id`
   - `GET /api/v2/scenarios/{scenario_id}` → `scenario_version_id`（前端 `ScenarioDetail.scenario_version_id`）

> ✅ 成功标准：拿到非空的 `scenario_version_id`，且场景 `given_model`/`expected_state` 含业务状态（如 `{ "user.status": "normal" }`）。

## Part C — 数据链验证（V32-002/003/005…012/014）

**UI**：`/missions/{mission_id}/data`

1. **派生数据需求**：`POST /api/v2/scenarios/{scenario_version_id}/data-requirements/derive`
   - `GET /api/v2/scenarios/{scenario_version_id}/data-requirements` → 应返回 `entity_type` + `constraints_json`（如 `membership.status=EXPIRED`）
   - ✅ 成功标准：候选均为**业务字段**，不含 `SELECT/UPDATE`；重复 derive 幂等。
2. **修订需求**（可选）：`PATCH /api/v2/data-requirements/{id}` `{ "entity_type": "member", "constraints": {"status":"EXPIRED"}, "required": true }`
3. **生成数据计划**：`POST /api/v2/scenarios/{scenario_version_id}/data-plans` `{ "environment_id": <test环境> }`
   - `GET /api/v2/data-plans/{id}` → `strategy`（EXISTING/API_BUILDER/DB_FIXTURE/WORKFLOW）、`risk_level`、`steps`、`plan_hash`
   - ✅ 成功标准：相同输入生成的 `plan_hash` 一致；高风险（P0/P1）需审批。
4. **批准计划**（高风险）：`POST /api/v2/data-plans/{id}/approve`
5. **触发 provision / 执行**：
   - UI：Mission 数据页「生成数据计划」后，到执行中心对场景发一次 Run：
     `POST /api/v2/scenarios/{scenario_id}/runs`
   - 运行会按 V32-014 走 `DATA PLAN → DATA FIND/CREATE → LEASE → DB BEFORE → ACTION → DB AFTER → ASSERT DB → CLEANUP` 时间线
   - ⚠️ **已知缺口**：目前**无独立 `POST /api/v2/fixtures`（provision）接口**——fixture 由 Run 执行触发；若要单独造 fixture，需补该 provision 端点。
6. **Fixture 查看**（执行后有 fixture 时）：
   - `GET /api/v2/fixtures/{fixture_id}` → `{status, strategy, manifest_json, entities[]}`；前端 `/fixtures/{fixture_id}` 渲染 `FixtureStatusBadge/FixtureManifestViewer`
   - ✅ 成功标准：`manifest_json` 为实体数组（前端解析为对象）、`entities[]` 含 `entity_type/logical_key/physical_ref_json/created_by_fixture/cleanup_action_json`
7. **快照 / DB 对比**：`GET /api/v2/fixtures/{fixture_id}/snapshots` → 按 `snapshot_type`(BEFORE/AFTER/CLEANUP_VERIFY) 配对，前端 `DbSnapshotDiff` 展示新增/删除/变更键
   - ✅ 成功标准：同一实体存在 BEFORE+AFTER 时能出 diff；`snapshot_json` 前端解析为对象
8. **租约 / 释放 / 清理**：
   - 租约：`POST /api/v2/fixtures/{fixture_id}/lease` `{ "run_id": 100 }` → `{status:ACTIVE}`
   - 释放：`POST /api/v2/fixtures/{fixture_id}/release` `{ "lease_id": <id> }`
   - 清理：`POST /api/v2/fixtures/{fixture_id}/cleanup` → `{status:SUCCEEDED, idempotent}`
   - ✅ 成功标准：连续 3 次清理结果一致（幂等）；不同 `run_id` 独占租约 409。

## 已知缺口 / 注意

- **无独立 fixture provision 端点**：fixture 目前由 Run 执行（V32-014）触发；纯前端无法单独造 fixture，需通过执行或补充 `POST /api/v2/fixtures`。
- 数据写操作仅限**测试环境**；生产环境数据源仅 `READONLY`，禁止 `DB_FIXTURE/WORKFLOW`。
- 前端对 `*_json` 字段已在 API 层统一解析为对象（`constraints_json/manifest_json/snapshot_json/config_json` 等），联调时以后端「字符串 + secret_ref 引用」为准，**不要把密钥放进 `config`**。
