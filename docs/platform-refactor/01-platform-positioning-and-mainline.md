# 平台定位与主链路产品化方案

## 1. 一句话定位

> 平台 = **「AI 版本验收工作台」**：以「版本」为唯一主线，让黑盒/业务测试工程师用业务语言完成
> 「建任务 → 审方案 → 看执行 → 下结论」，AI 负责用例生成、自动执行、证据整理与知识复用；
> 平台产出 = 「可放行的验收证据包 + 越用越准的业务知识库」。

## 2. 三个"不是"（过滤需求）

| 不是 | 说明 |
|------|------|
| 不是「用例管理 + 接口工具 + UI 工具 + Agent 平台的并列集合」 | 旧定位（模块工具集合），是上手难与迷茫的根因 |
| 不是「AI 引擎/开发框架控制台」 | Mission/Contract/Oracle/Runtime/Campaign 是引擎内部状态机，只作底层，不作产品界面 |
| 不是「AI 能力展示场」 | 每个页面必须回答「服务版本放行的哪一环」；答不上来 = 冻结或收专家模式 |

## 3. 双界面（按角色分层）

### 3.1 测试工程师界面（默认，≤5 个一级入口，全业务语言）

| 入口 | 回答的问题 | 现状对应 |
|------|-----------|---------|
| 我的待办（首页） | 今天要审什么、什么在跑、什么失败 | 工作台（改造，不做数字宫格） |
| 版本验收 | 我负责的版本怎么建、怎么测、能不能放行 | 智能测试任务 + 版本发布包 + 用例/计划（收敛） |
| 结果与缺陷 | 跑完的结果、证据、录了什么缺陷 | 执行记录 / 报告中心 / 缺陷管理（聚合） |
| 知识复用 | 上版怎么测的、这版改了哪、哪些可直接复用 | 知识中心（普通视图 3 个 Tab） |
| 资产与更多 | 环境、账号、数据、专家工具（可搜索） | 其余全部模块收进这里，按权限 + 搜索出现 |

原则：**功能在场景里出现，不提前平铺**。用户不需要预知"定时任务"，直到版本任务里需要"每周自动跑一次"。

### 3.2 专家/系统界面（权限门禁，不占默认导航）

- 资产库：用例服务、接口测试、UI 自动化、数据集、环境（AI 主链路自动调用）；
- 引擎专家：Durable Runtime、执行中心、Campaigns/Flaky/Healing、AI 配置、模型评估、生产证据、蓝湖证据；
- 系统治理：系统管理、集成配置、通知配置、角色权限。

## 4. 唯一主链路：版本验收任务（数据脊梁）

```
VersionTask 版本验收任务（唯一事实源）
 ├─ 需求源   PRD / 蓝湖原型 / 接口文档 / 变更范围
 ├─ 验收方案 AI 生成功能/接口/自动化场景（人工逐条审后冻结，含置信度与待确认问题）
 ├─ 执行记录 自动执行 + 证据（截图/请求/回放），失败自动分类（业务/脚本/数据/环境）
 ├─ 缺陷     业务失败一键转缺陷草稿
 └─ 放行结论 覆盖/通过率/风险 → 验收证据包（绑定发布包）
        │  任务完结自动沉淀
        ▼
   知识记录（版本怎么测的 + 下版复用建议）→ 下个版本任务自动引用
```

- 新 AI 生成一律写 Scenario/版本任务，旧 TestCase/TestPlan 降级为「资产库/历史批次」（详见 02 白名单）；
- 用户只在任务里做「采纳/修改/删除/追问」与「放行/打回」两种简单决策。

## 5. 在"dev 实现 → 测试介入 → 通过 → 合并发布"流程中的插入点

| 环节 | 痛点 | 平台提供 | AI 角色 |
|------|------|---------|--------|
| dev 开发中（前置） | 测试干等、需求歧义晚暴露 | 需求一进来就出「验收点草案 + 待澄清问题」 | 提前评审需求 |
| dev 提测 | 环境/P0 靠人试 | 提测自检：环境指纹 + P0 冒烟 + 影响面回归 | 不合格自动打回 |
| 测试设计 | 写用例最耗时 | AI 出可审阅方案，人只审 | 从「写」变「审」 |
| 执行 | 重复手工 | 一键跑版本任务 + 证据留档 | 人只处理需人工确认项 |
| 缺陷 | 人工归类抄录 | 失败自动分类 + 一键生成缺陷草稿 | 从「记」变「确认」 |
| 回归 | 不知影响面 | 智能回归按变更影响跑相关场景 | 回归量精准子集 |
| 验收 | 报告人肉拼 | 自动生成放行证据包 | 人只做放行/打回 |
| 发布后 | 经验流失 | 版本记录沉淀，下版自动带出 | 知识越用越准 |

## 6. 知识闭环（副产品化 + AI 任务探索双输入）

- **版本沉淀**：版本任务完结自动生成「版本知识记录」（需求→方案→结果→缺陷→放行结论）；
- **AI 任务探索沉淀（用户定稿新增）**：DSH 团队任务 / 版本任务探索 / 契约发现 / UI 观察 / 缺陷分析 等 AI 任务
  发现的新知识（新实体、新边界、新规则、新缺陷模式、新环境事实）自动捕获为「知识候选」→ 知识中心
  AI 审核台去重/初审 → 通过后沉淀为项目知识；
- **用户动作**：只做「审核通过/驳回」，不做知识维护；点确认即隐式知识标注；
- **下版复用**：建任务时 AI 自动带出「历史版本记录 / 已验证场景 / 缺陷边界 / 复用建议」。

## 7. 新业务接入（平台可长大的关键）

新被测业务线走「业务接入向导」4 步，不改平台内核：

```
1 建项目 + 拉团队 + 定角色
2 配置被测系统：环境地址/账号/网络访问（内网直连/VPN/生产只读）+ DB/Redis 只读
3 导入资产：OpenAPI → 接口资产与用例；蓝湖/PRD → 需求源；历史用例/脚本 → 迁移；选 P0 冒烟集
4 跑通首个冒烟版本任务 → 生成【业务基线】（契约快照 + P0 冒烟 + 环境指纹 + 首批用例库）
```

- 第二版本起，测试员只做一件事：在该业务下建「版本验收任务」，AI 自动带出业务基线 + 历史知识；
- 平台新功能一律挂 5 个主线节点或资产库，禁止新增并列顶级菜单；
- 试点：basketball-service / camel-mimo 已有 API 资产可作接入向导样本。

## 8. 必须停止的模式

1. 停止新增并列顶级菜单/独立模块页；
2. 停止让普通测试员接触引擎概念（词表见 03 文档）；
3. 停止扩大知识中心对普通用户的管理负担（普通视图只留 3 Tab）；
4. 停止无真实业务/无小白走查的"AI 自证"式验收；
5. 停止无限堆叠 C 条件式的功能堆叠——用「服务版本放行哪一环」过滤新需求。
