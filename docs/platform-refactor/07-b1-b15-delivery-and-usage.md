# B1-B15 交付与使用手册

## 平台现在解决什么问题

测试平台的主线是“版本验收任务”：从需求生成可审方案，运行后汇总证据和缺陷，再给出可审计的放行结论。tester 登录后默认只看到工作台、版本验收、结果与缺陷、知识中心、资产与更多五个一级入口。

## 完成一次版本验收

1. 在“版本验收”创建任务，填写版本号、变更模块，并关联已经导入的需求文档。
2. 生成 AI 方案，逐条检查标题、断言、置信度和待确认项；不合理的条目应修改或删除。
3. 确认方案后进入“执行与证据”。只有包含真实接口地址、方法、断言或页面执行目标的条目才能实际运行。
4. 对失败项检查请求、响应、步骤、截图或 Runner 错误，再创建缺陷草稿并同步缺陷库。
5. 查看证据包的检查总数、通过率、风险和缺陷。存在失败、跳过、阻塞，或没有真实通过项时，“放行”不可用。
6. 根据事实选择放行、有条件放行或打回。结论写入版本知识，并用于后续版本的复用建议和推荐回归。

## 新业务接入

接入页按“登记业务→接基线→生成方案→跑基线”四步执行。OpenAPI 地址和被测服务地址必填：

- 接基线会真实读取并导入 OpenAPI，不接受空文档或无 endpoint 的文档。
- 生成方案会使用导入的接口契约和需求上下文。
- 跑基线只有在所有检查真实通过时才把业务标为“已启用”；其他结果显示“已阻塞”。
- 步骤必须按顺序完成，完成后不会继续显示“下一步”。

## 如何理解状态

| 状态 | 含义 | 应做什么 |
|------|------|----------|
| 待评审 | AI 方案还需人工判断 | 逐条确认，不要直接运行 |
| 已执行 | 已有一次运行结果 | 检查证据与失败分类 |
| 已阻塞 | 缺执行目标、环境或必要证据 | 补齐目标/环境后重跑 |
| 有条件放行 | 已知风险被明确接受 | 记录责任人和后续动作 |
| 打回 | 当前版本不可发布 | 修复缺陷后重新验收 |

## 体育 16.0.0 本次结果

本次需求成功生成并审核 30 条方案，但这些条目没有真实执行目标，因此系统正确给出 30 blocked、0 pass，并禁用直接放行。AITDE 的 AI Provider 返回非法/空内容和 HTTP 400，本地也没有 Temporal Worker；这些情况均保留为失败或阻塞，没有被降级结果掩盖。

要完成体育 16.0.0 的真实闭环，需要提供可访问的体育 OpenAPI、被测环境、健康 AI Provider 和 Worker/Runner，然后从同一需求重新执行。详细证据见 `work-logs/evidence/batch-226-sports-v16-ai-e2e/README.md`。
