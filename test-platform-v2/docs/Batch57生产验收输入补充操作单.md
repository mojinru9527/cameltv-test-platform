## 1. 当前不需要补充的内容

- 测试平台自身的 production 服务器、域名、TLS 和 PostgreSQL 尚未采购，
  统一记为 `DEFERRED / UNPROVISIONED`，本轮不需要填写生产测试平台 URL。
- 双 VPN 切换手册保持 `paused`，未重新启用前不执行 vpn07/OpenVPN 切换。
- P0 浏览器验收只看 PC `1440×900`；tablet/mobile 降为 P2，不阻塞交付判定。
- 本地测试平台固定使用 `http://localhost:5173/`、后端
  `http://127.0.0.1:8000` 和独立 local 数据库。

## 2. 安全填写规则

可以在聊天中提供：

- 环境或服务的逻辑名称；
- URL 是否可访问、所属网络和允许的操作范围；
- OpenAPI 服务名称、接口公开/受保护分类；
- 数据库版本、快照时间、行数基线和文件 SHA-256；
- 允许执行的验收窗口和清理要求。

不要在聊天、Git、截图或验收报告中提供：

- 密码、短信验证码、Token、Cookie、Authorization；
- AI API Key、数据库完整连接串、SMTP 密码、Webhook Secret；
- OpenVPN 配置正文、私钥、隧道 IP；
- 原始生产业务数据或未脱敏数据库。

秘密值只在本机未跟踪的 `.env`、测试平台加密变量或批准的凭据管理工具中
填写。每组输入只需先回复“组号 + 非敏感信息已准备好”，再按该组步骤处理。

## 3. P0 输入组

### I01：体育测试节点、六服务 OpenAPI 与鉴权边界

对应：`B56-B01`、`B56-B02`、`B56-B03`。

这组不是要求用户手工统计接口，也不是要求用户制作 OpenAPI 文件。用户只需
回答以下四项：

| 用户需要确认的字段 | 填写要求 |
| --- | --- |
| 六个服务名 | 确认是否仍为 `camel`、`live`、`payment`、`studio`、`konfi`、`account`；如有改名只给新逻辑名 |
| 入口获取方式 | 提供当前六个 Knife4j/OpenAPI 入口，或授权 QA 在 OpenVPN 窗口重新发现；无需用户计算版本、路径数和 SHA-256 |
| 测试鉴权方式 | 说明使用账号登录、统一 Token 还是各服务独立 Token；密码、Token 不发聊天 |
| 操作边界 | 明确创建、修改、查询、删除，以及支付/退款/转账/封禁/发布/开播/批量操作各自是否允许 |

如入口只能在 OpenVPN 下访问，只登记网络条件。双 VPN 手册仍为 `paused`，
只有用户明确回复“启用 OpenVPN 验收”后才执行网络切换和采集。

以下内容由 QA 自动产出，不要求用户填写：

- 六个节点的可用状态和失败原因；
- 实时 OpenAPI 的采集时间、服务版本、路径数、操作数和 SHA-256；
- 公开接口与受保护接口的真实响应差异；
- 无效凭据、最小权限凭据和越权请求的结果；
- 可恢复测试数据的创建、修改、查询和清理证据。

完成标准：节点 6 恢复；6 份契约均可解析；公开/受保护声明与真实响应一致；
无效凭据被拒绝，合法最小权限凭据通过。

### I03：用户端与运营后台设计源

对应：`B56-B09`、`G56-011`。

这组要验证的不是“页面能否打开”，而是平台从设计稿提取出的页面、文字和需求，
能否追溯到真实设计源。用户先从下面两种验收目标中选一种：

#### 方案 A：只验核心页面的设计一致性（推荐当前 Batch 57）

用户需要提供：

1. 用户端 3～5 个核心 PC 页面名称，例如首页、登录、赛事详情、个人中心；
2. 运营后台 3～5 个核心 PC 页面名称，例如登录、首页、列表、编辑页；
3. 每端一个只读蓝湖/设计源入口，或上述页面的脱敏导出图；
4. 当前认可的版本号或更新时间；
5. 是否允许把脱敏截图送入本地 OCR。

QA 负责抓取页面树、截图/OCR、来源时间和 SHA-256，并逐页比对标题、主要字段、
按钮、布局层级和关键交互。当前只阻塞 PC `1440×900`，tablet/mobile 作为 P2。

#### 方案 B：验完整的设计来源可追溯性

除方案 A 外，还需要设计源中的完整页面树、需求/Wiki 对应关系和历史版本范围。
适合发布前做全量审计，但输入量和验收时间更大。

如果暂时没有蓝湖登录态，可先提供脱敏导出图；报告会写明“静态证据验收”，
不能声称已验证设计源在线权限或版本历史。

### I04：真实 AI/OCR 服务

对应：`B56-B05`、`G56-011`。

建议组合：

- 语义分析：`deepseek-v4-pro`，用于需求文档结构化提取、矛盾检查、验收点生成、
  知识条目归纳和最终复核；
- OCR/版面分析：本地 PaddleOCR `PP-StructureV3`，用于中文截图、表格、版面、
  公式和图表解析，并输出 Markdown/JSON；
- 知识库检索：Batch 57 暂时保留现有 `BAAI/bge-small-zh-v1.5`，避免在本轮同时
  迁移向量维度和重建索引；`BGE-M3` 另立迁移任务评估。

DeepSeek 是文本分析模型，不替代 OCR。当前测试平台采用 OpenAI 兼容接口，
最小可用配置为：

| 字段 | 要求 |
| --- | --- |
| Provider | DeepSeek API；网页版/客户端会员不能直接替代 API 凭据 |
| Endpoint | `https://api.deepseek.com` |
| Model | `deepseek-v4-pro` |
| Key | 只填入本机 `AI_API_KEY` 或平台加密变量，不发聊天、不提交 Git |
| 数据边界 | 是否允许发送脱敏截图、附件、需求文本 |
| 限额 | 速率、额度、超时和重试要求 |

OCR 走独立本地命令适配器，不把原始生产截图默认发送到外部服务。若以后需要
复杂视觉文档理解，可单独评估 PaddleOCR-VL；不在本轮默认扩大范围。

完成标准：最小脱敏输入产生可追溯真实输出；主断言不使用规则 fallback 或
mock；无 Key、无权限、超时场景诚实失败。

参考：

- [DeepSeek API 当前模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)
- [DeepSeek API 更新记录](https://api-docs.deepseek.com/updates/)
- [PaddleOCR PP-StructureV3 官方说明](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)
- [FlagEmbedding / BGE-M3 官方仓库](https://github.com/FlagOpen/FlagEmbedding)

### I05：旧 PostgreSQL 脱敏快照

对应：`B56-B08`。

当前确认：没有可用于验收的旧 PostgreSQL 脱敏快照。

因此本项记为 `INPUT UNAVAILABLE`，不是测试失败，也不能标为通过。后续二选一：

1. 产品负责人确认旧库升级兼容不属于本次发布范围，形成正式豁免记录；
2. 未来取得合规脱敏快照后，补做恢复、升级、数据保留和重复升级测试。

如果选择补测，需要准备：

| 字段 | 要求 |
| --- | --- |
| 数据库版本 | PostgreSQL 主版本和扩展清单 |
| 快照 | 已脱敏、可在隔离环境恢复的 dump/backup |
| 完整性 | 文件大小、SHA-256、导出时间 |
| 基线 | 关键表名和各表行数；不含真实正文 |
| Schema 版本 | 当前 Alembic revision/head 或历史说明 |
| 恢复说明 | 所需角色、扩展、编码和恢复命令的非秘密部分 |

不要提供生产连接串。完成标准：隔离恢复、升级、数据保留、重复升级、唯一
Alembic head 和 ORM 零漂移均通过。

### I06：生命周期通知验收端点

对应：`C55-4`、`G56-012` 的定时任务/通知部分。

本轮选择 SMTP 测试邮箱。按以下顺序准备：

1. 创建一个专用测试发件箱；推荐再准备一个独立收件箱，便于验证真实投递；
2. 在邮箱服务商处开启 SMTP，并生成“应用专用密码/授权码”，不要使用或发送
   个人邮箱登录密码；
3. 确认 SMTP 主机和端口。当前代码支持 `587 + STARTTLS`；如果服务商只支持
   `465 + implicit SSL`，需要先补代码，不能直接填 465 假设可用；
4. 在本机未跟踪的 `.env` 中填写：

   ```dotenv
   SMTP_HOST=
   SMTP_PORT=587
   SMTP_USER=
   SMTP_PASSWORD=
   SMTP_FROM=
   SMTP_USE_TLS=true
   SMTP_VERIFY_CERT=true
   ```

5. 在测试平台通知通道中填写收件地址；不要提交到 Git；
6. 给出允许测试的时间窗、主题前缀（建议 `[CamelTv-B57-TEST]`）和测试邮件清理
   规则；
7. 依次验证 `task_started`、`task_finished`、`test_result`、`plan_done`、
   `schedule_failed`、`report_generated` 等生命周期事件；
8. 验证错误收件地址或临时不可达时状态、审计和重试可追溯，且不重复执行核心
   任务；
9. 验收结束后撤销授权码或关闭测试通道，并清理测试邮件。

用户只需要回复 SMTP 主机、端口、发件地址和收件地址是否已准备好。账号密码/
授权码只在本机填写。完成标准：调度只触发一次，成功/失败状态、审计和通知
可追溯；端点失败可重试且不重复执行核心业务。

## 5. 建议补充顺序

1. 先选择 `I03` 方案 A 或 B；
2. 确认 `I04` 使用 DeepSeek API 的 `deepseek-v4-pro`，并说明可发送的数据边界；
3. 准备 `I06` SMTP 主机、端口、发件箱和收件箱；
4. 确认 `I01` 六个服务名及是否授权以后进入 OpenVPN 重新发现；
5. `I02`、`I08` 等用户明确重新启用 OpenVPN 验收后执行；
6. `I07` 周末设备到位后执行；
7. `I09` 明确高风险操作边界后，在 vpn07 下单独执行；
8. `I05` 选择正式豁免或未来补测。

每完成一组，都重新固定代码 SHA、执行时间和输入版本，并只保存脱敏证据。
输入变化后，旧验收结果不自动沿用。
