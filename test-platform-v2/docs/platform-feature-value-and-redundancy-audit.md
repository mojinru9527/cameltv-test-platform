## 1. 评估方法

1. **源码核查**：每个模块的前端页面（`frontend/src/pages/*`）、后端路由（`backend/app/api/v1/*`）、
   模型与服务，确认"功能确实存在且接真实引擎"。
2. **真实使用证据**：2026-08-12 生产浏览器审计（`work-logs/evidence/browser-audit-2026-08-12/`）
   逐模块抓取截图+页面文本；工作台/追溯页给出真实计数（用例 8108~8562、AI 导入用例 476~703、
   图谱 966 节点等）。
3. **批次证据**：C-CONDITIONS 中该模块对应的 C 条件与关闭批次（如 C147-8 数据集参数化、
   C151-1 UI 用例映射回写、C146-1 计划执行预检）。
4. **冗余判定**：按"数据对象、操作入口、权限模型、使用场景"四个维度两两比对。

> 诚实声明：报告中心/集成配置/通知配置/测试数据集目前在生产中为 **0 条数据**（审计截图可见空态）。
> 这代表"尚未被团队使用"，不代表功能无价值；本评估给出每个功能的**效率主张 + 可验证证据**，
> 对"0 数据"模块明确标注"价值待使用验证"。

## 2. 八个功能逐项解释 + 效率价值证明

### 2.1 测试数据集（`/dataset`，`dataset.py` / 数据集模型）

**用途**：上传 CSV/JSON 结构化测试数据，把"同一接口/场景的多组输入"抽出来统一管理，
执行时按行注入（Batch 154 打通 API 用例 `dataset_id` + `${变量}` 绑定，见 C147-8）。

**效率主张**：没有它，N 组数据 = N 条用例或 N 次手工改参；有它 = 1 条用例 + 1 个数据集，
执行任务一次跑 N 行。接口回归 899 个资产的场景下，这是把"手工改参回归"变成"数据驱动回归"的关键。

**证据**：Batch 154 已实现 CaseDrawer/ApiCaseTab 数据集选择 + 执行兜底（C147-8 Closed，commit a91125a）。
生产截图（survey-dataset.txt）当前为 0 条 → **价值待使用验证**。

**冗余**：与"目标环境变量"（environment_variable）互补不重叠：环境变量是"会话级/全局密钥+地址"，
数据集是"用例级多行参数"。无重复。

### 2.2 Agent 工作台（`/agent-workbench`，`agent.py` / agent 队列模型）

**用途**：7 个受控 Agent：需求分析、影响分析、用例生成、失败分析、Wiki 编译、知识差异对比、
平台知识分析。产出先进"AI 审核台"，人工采纳后才入库。

**效率主张**：把"读需求→拆功能点→写用例"从人工小时级压到分钟级；差异对比把"两个版本需求
逐条人工比对"变成自动 diff。

**证据（强）**：
- 生产"知识中心-概览"：Agent 执行总量 **12 次**、AI 产物采纳率 **99%**、平均耗时 **17.5s**（final2/knowledge_tab_overview.txt）。
- Agent 工作台执行历史：需求分析 40.4s/5.9s 成功、knowledge diff 8.2s（final-snapshot.json）。
- 需求文档页：AI 导入用例 **476 → 703** 条（survey→final2 两次抓取），对应 6~7 份需求文档、54~105 业务域。

**冗余**：与"Playground/接口用例生成"不重叠（Agent=批处理+审核流；Playground=单条草稿编译执行）。
与"知识中心 AI 审核台"是上下游关系（Agent 产 → 审核台审），非重复。

### 2.3 蓝湖证据包（`/lanhu-evidence`，`lanhu_evidence.py`）

**用途**：采集蓝湖设计稿（截图+OCR）→ 人工审核 → 导入需求/RAG/Wiki，供用例生成和知识检索。

**效率主张**：蓝湖 Axure 原型几十上百页，人工截图/抄文案是小时级体力活；本功能自动捕获页面 +
OCR 文本，失败可重试，把"设计稿 → 结构化需求"压缩到分钟级且留证据链。

**证据**：生产任务 #24（1/1 页 OCR1 成功）、#28（7/7 页 OCR7 成功）、#26/#29/#30 失败留痕
（survey-lanhu-evidence.txt、final-snapshot.json）；需求文档页证据任务面板与"查看截图"入口。
蓝湖链接是 Agent 需求分析（40.4s 成功）的输入，形成"蓝湖→证据→需求→用例"链路。

**冗余**：与"需求文档"是输入/加工关系；与"知识中心"是上游。无重复模块。

### 2.4 目标环境（`/environment`，`environment.py` / 环境变量模型）

**用途**：项目级环境（dev/test/staging/prod）+ 加密变量（Token/密码），API/UI 执行统一引用
`${VAR}`；生产环境高风险执行弹确认。

**效率主张**：没有它，每个用例/任务里硬编码环境地址和 Token，换环境=全局改用例；
有它=环境一次配置、处处引用，Token 加密存储防泄漏。这是接口/UI 自动化能安全跑生产的前提。

**证据**：生产已配置 3 个环境（体育平台-生产、体育平台-Test5、体育平台-生产-站点UI）+
`PROD_ALLOWED_HOSTS`、`PROD_LOGIN_AUTHORIZED` 等变量（survey-environment.txt）；
UI 任务全部绑定 PROD 环境，接口用例执行按环境切换。

**冗余**：与"测试数据集"互补（见 2.1）；与 v1 `test-platform/config/environments/*.yaml` 存在
**跨版本配置双轨**（验收文档已登记 g3-test3 vs test5 不一致），建议后续统一由平台环境页管理。

### 2.5 版本测试任务 / 版本发布包（`/release-bundles`，`release_bundles.py` + `version_mission.py`）

**用途**：围绕一个发布版本（如 16.0.0）组织：版本范围、蓝湖原型模块树（45 模块/43 页）、
生产页面清单、生产差异标注（C102-4）、交互覆盖缺口（C119-2，2217 条边）、测试任务与质量结论。

**效率主张**：版本回归最怕"不知道这次改了哪些页面/接口"。发布包把"蓝湖版本"变成可追踪对象，
生产差异标注自动算出 15.0.0→16.0.0 变更页，交互覆盖缺口给出 2217 条未覆盖跳转边——这些
靠人工对照原型根本做不完。

**证据**：生产发布包 5 个：体育平台-16.0.0-开发验收（草稿）、体育平台-15.0.0-上线回归（活跃）、
16.0.0、体育平台-需求基线（活跃 45 模块/43 页）、体育平台-功能地图（final2/release-bundles.txt）；
需求文档页"生产差异标注"选择了 16.0.0 并展示 2217 条缺口（final2/requirement.txt）。

**冗余**：与"测试计划"不同：计划管"用例执行"，发布包管"版本范围+差异+交付结论"，
计划通过"执行登记"回链到版本（batch-157 执行模型双向关联）。与"报告中心"是输入输出关系。

### 2.6 报告中心（`/report`，`report.py` / 报告模型）

**用途**：由测试计划生成快照报告：通过率、质量门禁（通过率阈值/P0/P1 上限）、趋势图、缺陷收敛。

**效率主张**：发布结论要"有数字"。没有报告模块，每次发布前人工汇总 Excel；
有它=一键生成+门禁自动判。

**证据**：生产 0 份报告（survey-report.txt 空态）→ **价值待使用验证**；但 batch-151 已打通
"计划执行失败 → 自动转缺陷/报告/通知"，报告是失败自动链路的落点之一。
报告中心与"质量追溯/工作台"存在**数据重叠**（都展示通过率/覆盖率），建议后续统一口径复用，
而不是删除。

### 2.7 集成配置（`/integration`，`integration.py` / 集成配置模型）

**用途**：Jira/TAPD 外部缺陷双向同步 + 模块联动追踪（需求→用例→执行，实时展示关联率/覆盖率）。

**效率主张**：测试发现的问题自动同步到研发的 Jira/TAPD，省掉"平台录一遍、Jira 再录一遍"。

**证据**：生产"模块联动追踪"在跑：6 需求 / 7879 用例 / 用例关联率 6% / 需求覆盖率 33% /
已联动用例 476（survey-integration.txt）；外部集成配置 0 条（未接 Jira/TAPD）→ **价值待使用验证**。

**冗余**：与"通知配置"都是"外部系统出口"，但对象不同：集成=缺陷/资产同步，通知=消息推送。

### 2.8 通知配置（`/notify`，`notify.py` / 通知渠道模型）

**用途**：SMTP/Webhook（钉钉/飞书）通道 + 事件订阅（任务开始/结束、测试结果），失败自动链路出口。

**效率主张**：任务跑完自动@群/发邮件，团队不必盯着平台刷结果；批量回归尤其需要。

**证据**：生产 0 渠道（survey-notify.txt 空态）→ **价值待使用验证**；batch-151 失败自动链路
（转缺陷/报告/通知）已实现，通知配置页已支持 Webhook/飞书订阅（final2/testplan.txt 可见
"质量通知 Webhook 飞书 任务已发起/任务已结束/测试结果"）。手册 §8 给出钉钉/SMTP 配置步骤。

**冗余**：与"定时任务/计划执行"是出口关系；与"集成配置"对象不同（见 2.7）。

## 3. 用户疑问专项解答

### 3.1 测试计划"TP-SPORTS-1600 体育平台-16.0.0-开发验收计划"用例全是跳过，功能有什么用？

**功能定义**：测试计划 = 把用例按版本/阶段组织起来 → 选环境一键/批量执行 → 记录每条用例
通过/失败/跳过/阻塞 → 失败自动转缺陷/报告/通知（batch-151，计划级开关）。

**为什么全是跳过/待执行（证据）**：
- 生产抓取时该计划状态"进行中"，进度 **0/405**（final2/testplan.txt），即 405 条用例已入计划但**从未真正执行**。
- 执行前置条件：**必须选择目标环境 + Token 就绪**。batch-148 已把"环境/Token 预检"做成执行前硬检查
  （C146-1/C147-2 Closed，commit e601f96），未选环境或 Token 失效时执行会直接失败/跳过，
  不再"假装执行成功"。
- 同一时段 15.0.0 计划 2615 条也全是 pending（截图 51-plan-3-after-exec.png），说明是**执行未发起**，
  不是计划功能坏。

**结论**：计划的价值在"编排+执行+结果闭环"，不是"用例列表"。全跳过有两种原因：
1. 纯人工用例计划：批量执行按设计把人工用例标记为"跳过"（弹窗文案"全部用例（API/UI 自动，人工标记跳过）"），
   需要逐条点击用例行「执行」按钮记录结果；或把 API/UI 自动化用例加入计划后批量执行。
2. 未选择环境/Token 未就绪：batch-148 已把"环境/Token 预检"做成执行前硬检查（C146-1/C147-2），未选环境会失败/跳过。

**本批修复**：环境选择入口原只在计划含 API 用例时显示（`hasApiCases`），纯人工用例计划看不到"环境选择"。
已改为含 API/UI 自动化用例即显示环境选择，并在执行弹窗对纯人工计划增加明确提示（见 batch-165 PlanDetail.tsx）。


### 3.2 版本测试任务对效率有什么作用？

见 §2.5。一句话：**版本回归的"范围"和"差异"由它自动生成**（生产差异标注 + 2217 条交互缺口 +
45 模块/43 页模块树），人工做不出来；测试计划负责"执行"，版本任务负责"结论"，二者串成
15.0.0/16.0.0 的验收闭环（生产已有两个验收项目）。

### 3.3 系统管理 / 项目管理 / 组织管理 / 我的项目——冗余评估与收敛建议

| 入口 | 数据对象 | 主要操作 | 真实使用（生产证据） |
|------|---------|---------|---------------------|
| 系统管理 `/system` | 用户、角色、审计、API Token、邀请码 | 平台级管理员 | 7 个用户、4 角色在管（survey-system.txt） |
| 项目管理 `/project` | 当前项目配置、成员、质量门禁 | 项目级配置 | 3 个项目，质量门禁配置页 |
| 我的项目 `/my-projects` | 项目列表、创建、切换 | 普通用户 | 项目列表+进入（同一批 3 个项目） |
| 组织管理 `/organizations` | 组织（personal/team）、组织成员 | 组织级 | 3 个"我的组织"，全部 personal 类型，0 团队组织 |

**重叠点**：
1. `项目管理` 和 `我的项目` **双入口管理同一批项目**（列表+成员+进入），生产两个页面显示几乎相同的 3 个项目。
2. `组织管理` 目前只有个人组织（personal-1/10/11），团队组织 0 个——组织概念当前没有实际租户价值。
3. `系统管理` 的"用户管理"与 `项目管理` 的"成员管理"在权限模型上分层（平台用户 vs 项目成员），
   但普通用户会混淆。

**收敛建议（本期不实现，仅评估）**：
- 保留 `我的项目` 作为**唯一项目入口**（创建/切换/成员/质量门禁都放这里）；
- `项目管理` 菜单隐藏或重定向到 `我的项目`（省一个入口）；
- `组织管理` 折叠进 `我的项目` 的"所属组织"字段（个人组织自动创建，团队组织做高级功能）；
- `系统管理` 只保留平台管理员（用户/角色/审计/Token/邀请码），普通用户不可见。
- 最终 4 个入口 → 2 个：`我的项目`（业务）+ `系统管理`（管理员）。

## 5. 结论与建议清单
