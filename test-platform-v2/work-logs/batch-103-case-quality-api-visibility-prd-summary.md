## 1. 问题陈述（用户验收反馈，2026-08-06）

用户在 Batch 102 验收时提出三点：

1. **用例生成是否遵循了团队用例规范与方法**：AI 生成功能用例未显式对齐 `tests/test-case-standards/`
   （测试用例标准 / 功能测试用例规范 / 功能测试检查点 / 接口测试规范 等）。
2. **覆盖度不合格**：用户端 16 模块 / 92 功能点仅生成 77 条用例（约 0.84 条/功能点），
   正负向与边界覆盖不足，需求未被完全理解透。
3. **接口用例不可视**：既有接口用例（Batch 101 导入的 325 条）看不到请求参数、断言、
   以及对应的请求结果（执行后的实际响应），无法直接用于接口自动化落地与评审。

2026-08-06 追加（用户细化）：

4. **接口用例必须按接口测试规范生成**（`tests/test-case-standards/接口测试规范.md`、
   `API接口测试方案.md`）：入参校验（空/null、类型、长度、值域、枚举、默认值、0/负数、
   组合、规则、特殊字符）、业务逻辑校验、返回值校验均为必选。
5. **请求参数必须以体育平台真实业务请求为基线**，不能模拟造参。示例
   `/camel-service/ee/news/list_visible` 真实请求参数：
   `{"sorts":[{"key":"top","sort":"desc"},{"key":"updateTime","sort":"desc"}],"page":2,"size":30,
   "queryList":[{"isOrNotRange":0,"key":"language","type":"String","value1":"0","value2":""}],
   "locale":"en"}` —— 需按这些字段的实际取值（page/size 分页、queryList 过滤条件、
   sorts 排序、locale 语言）设计正/负/边界与字段类型校验用例。
6. **全字段覆盖 + 生产回填原则（修订）**：接口清单按功能需求确定；能通过生产环境接口
   获取的真实请求/响应优先回填作为测试数据基线。但接口用例与接口调试的数据必须**覆盖
   对应接口的全部字段**：按字段在接口中的业务含义（该字段代表什么、类型、取值范围、枚举、
   格式、默认值、与其他字段的组合关系）构造**贴合接口语义的数据**进行测试，而不是直接
   mock 一个无业务含义的占位值（如随机字符串/数字）。生产回填提供真实基线，字段语义
   构造保证全字段覆盖与正负边界，两者结合避免测试偏移。

## 2. 成功指标

| 指标 | 基线 | 目标 |
|------|------|------|
| 用例规范对齐 | AI 生成无规范注入 | 生成提示词注入测试用例标准（正/负/边界、检查点）；产物可查证 |
| 功能用例覆盖度 | 用户端 77 条（0.84 条/FP） | ≥2 条/FP（用户端 ≥184 条），正负向+边界齐全；运营后台同步补强 |
| 接口用例可视 | 用例仅标题/步骤 | 每条接口用例展示：请求参数（入参示例/约束）、断言（响应校验）、实际请求结果（执行回填） |
| 接口用例真实参数 | 模拟造参 | 以生产真实请求参数为基线（如 list_visible 的 page/size/queryList/locale），字段级正/负/边界/类型/枚举/组合覆盖 |
| 全字段语义覆盖 | 无意义 mock 占位 | 接口用例/调试数据覆盖接口全部字段；按字段业务含义构造贴合数据（类型/含义/边界/枚举/格式/组合），生产回填做基线 |
| 平台可查证 | 无 | 平台用例库/接口用例详情页可直接查看上述字段 |

## 3. 用户故事 + 验收标准

- As a **资深测试工程师**, I want AI 生成用例遵循团队规范（正负向/边界/检查点），so that 用例覆盖真实业务逻辑且可直接评审。
- As a **QA**, I want 接口用例展示请求参数、断言与请求结果，so that 接口自动化断言落地有据可依。
- As a **QA**, I want 接口用例基于真实业务请求参数并按接口测试规范覆盖正负边界/字段类型，so that 符合生产现实而非模拟造参。
- As a **验收负责人**, I want 用户端覆盖度达标（≥2 条/FP），so that 第一期功能逻辑无遗漏。

Given AI 生成已注入规范并重跑用户端需求，When 查询用例库，Then 每功能点有正/负/边界用例且字段完整。
Given 接口用例执行后，When 查看用例详情，Then 请求参数、断言、实际响应可见。

## 4. 技术考量

- 后端：`ai_service` 生成提示词注入 `tests/test-case-standards/` 方法（等价类/边界值/场景法/错误推测），
  并增加「每功能点 ≥2 条、正负向+边界」约束；生成结果校验（覆盖缺口报告）。
- 接口用例：`AIGeneratedCase`/`TestCase` 增加请求参数与断言字段；执行结果（实际响应）回填展示；
  前端用例详情页渲染参数/断言/响应。
- 接口用例生成：以生产抓取的真实请求样本为基线（Batch 101 契约 + 生产调用记录），
  按 API接口测试方案 的入参/业务/返回值三档必选设计字段级用例；禁止凭空造参。
- 覆盖度：本地 AI 重跑用户端/运营后台（Batch 102 的 local-ai 通道已验证），按规范补生成并重导入；
  生产 300s 网关超时问题（C102-1）期间沿用本地生成+同步通道。

## 5. 范围
