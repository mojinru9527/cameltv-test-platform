## 1. 问题陈述

用户 2026-08-07 方向反馈（承接 Batch 112 Leader 条件 C112-1/C112-2）：

1. **用例生成思路偏差**：用户端需求、运营后台需求（运营后台 + konfi）、测试环境接口地址、
   真实体育平台用户访问地址这几个维度是互相补充、真正落地逻辑的。当前用例生成以需求为主，
   接口为辅，但**模块-接口-功能之间的关联关系没有先在知识中心里梳理清楚**，
   导致用例不齐全、有遗漏。应先在知识中心沉淀「体育平台模块-接口-功能」关联基座，
   用例生成基于该关联基座落地补充调整。
2. **用例缺 UI 交互维度**：现有用例只覆盖需求限制（字段/规则/正负向），
   没有覆盖用户使用时的页面交互——点击、跳转、入口可达性、跨模块导航。需要补充交互类用例。
3. **现状基础**：功能模块地图 v2（`docs/体育平台-功能模块地图.md`）已梳理三端定位、
   用户端 13 模块矩阵、运营后台 15 模块菜单、konfi 82 配置项关联、34 接口↔模块映射、
   需求 vs 生产差异——但该关联只在 Markdown 文档里，**未沉淀为知识中心可检索/可引用
   的关联基座**；交互路径（页面跳转）仅有 40 页路由勘察数据，未转成用例。

## 3. 用户故事 + 验收标准

- As a **用例生成者**, I want 知识中心里有体育平台模块-接口-功能的关联基座，so that 生成用例时
  先按关联关系定位模块/接口/功能，避免遗漏。
  - Given 功能模块地图 v2 的关联数据，When 导入知识中心并检索，Then sources 可见、关联实体/关系可查。
- As a **QA**, I want 功能用例覆盖页面交互（点击/跳转/入口可达），so that 用例不仅验证需求限制，
  还验证用户真实操作路径。
  - Given 生产 40 页路由 + 交互触发样本，When 梳理页面跳转路径，Then 按 P0 模块生成交互用例
    （入口→目标页可达、返回、跨模块导航），正负向齐全。

## 4. 技术考量

- **关联基座数据模型**：`module`（用户端/运营后台/konfi）→ `function`（功能点）→ `interface`
  （method+path，含真实参数样本引用）→ `backend`（运营后台菜单/页面）→ `konfi`（formKey）。
  来源=功能模块地图 v2 §2/3/4/5 + `evidence/batch-110/`（nav.json、konfi-inventory-sports.json、
  xhr-samples-final.json、production-pages.json）。
- **知识中心入库**：复用 capture 通道（C110-2 已验证 code 0 + sources 可见）；以「功能模块地图 v2 +
  关联数据集」为知识源文档入库，并记录 source id 与检索命中（RAG 关键词：模块名/接口路径/formKey）。
- **交互路径提取**：从 `evidence/batch-110/production-walkthrough-v2/production-pages.json`（40 页路由）
  + xhr-samples（page 字段）+ 功能地图 §2 页面列，构建「页面→入口→目标页」跳转清单；
  以 P0 模块（首页/赛事/直播/资讯/搜索/我的/联赛/回放/世界杯）优先。
- **交互用例生成**：按团队用例规范（tests/test-case-standards）生成交互域用例
  （正：入口可达/跳转成功/返回；负：直达无效 URL、无权限/空态；边界：断链/404 页）：
  每条含前置/步骤（含点击跳转）/预期/正负向/P0 标识，落库功能用例库（domain=交互测试或模块+交互）。
- **技能**：`test-case-design`（用例规范）、`playwright-cli`/`playwright-skill`（交互路径实测核对）、
  `cameltv-bug-guard`（后端/入库避坑）。
