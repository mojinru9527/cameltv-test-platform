# Batch 122 — PRD（体育用例重构：全模块深度用例 + 端/后台结构）

> **Product (🟦)** | Date: 2026-08-08 | Status: Review

## 1. 问题陈述

用户对测试平台生产环境做了走查，结论是**体育需求接入的用例「有数量、没深度」，知识中心「有功能、没内容」**，当前状态**不具备外放生产级接入条件**。本批次（A）聚焦用例本身；知识中心可用性（B）与需求/设计稿正式入库（C）为后续批次。

走查与仓库核对的硬证据：

| # | 问题 | 证据 |
|---|------|------|
| 1 | Pick/预测模块用例极少且无业务深度 | 平台 p0_modules 中 `Picks` 仅 2 条（登录/未登录点击）；`赛事预测` 21 条、`赛事详情` 30 条，均为「查看XX展示」级单步用例；接口用例 `下注` body=`{}`、断言仅 2xx+响应时间 |
| 2 | 需求文档中的完整规则未体现在用例 | 本地原型 `axure_extract_test/预测.html` 明确含：玩法说明（奖励=投入×实时赔率向下取整）、单场≤1000/单日≤20000 银钻、赛后 1 个自然日内结算、自动发放至银钻余额、确认参与弹窗 5 类异常处理、预测记录 5 种状态（预测中/待开奖/已开奖/已取消/已退款）、全部/本场筛选——用例全部缺失 |
| 3 | 用例无端/后台维度 | domain 仅 `用户端/运营后台/接口测试` 三个粗粒度；无 4 入口（安卓/iOS、PC-web、移动端-web）与 konfi/运营后台拆分 |
| 4 | 功能/接口用例未分离 | 同一模块下功能与接口混排（如 赛事详情 92 条混 25 条 API）；接口用例大量为「2xx 冒烟」 |
| 5 | 联赛/球队/球员未按页签梳理 | 原型含 联赛详情页/球队详情页/球员详情页(PC)/球员详情_pc 等，均有多个 Tab（积分榜/赛程/阵容/数据/资料/高阶数据包），现有用例未逐 Tab 覆盖 |
| 6 | 系统权限缺失 | PC-web/移动端-web 的权限获取（原型 `权限获取.html`、`启动页.html`、`开屏广告.html`）无对应用例 |
| 7 | 关联流程缺失 | 无「下注→结算→奖励发放→流水」闭环用例；无「赛事详情→预测→预测记录→个人中心银钻明细」跨模块用例 |
| 8 | 全模块覆盖不完整 | 弹幕/聊天室/数据/个人中心/商城/装扮/回放/世界杯等模块用例稀疏或缺失（40 页生产勘察 + 130+ 原型页 vs 用例模块仅 213 个 test_case_module 且多为单步） |

## 2. 成功指标

| 指标 | 基线（2026-08-08） | 目标 |
|------|--------------------|------|
| 用例结构 | domain 3 个粗粒度、模块无入口维度 | 功能/接口分离；功能按 4 入口 + 运营后台/konfi 拆域；模块路径 `入口/一级/二级` |
| 全模块覆盖 | 用例稀疏、单步为主 | 用户端/运营后台/konfi 全部模块均有「状态机 + 用户流程 + 异常 + 关联」深度用例 |
| 单模块深度 | Picks 仅 2 条；56% 功能用例为单步 | 每个核心模块 ≥1 条主流程闭环 + ≥N 条状态/异常/关联用例；单步「查看XX」类清零 |
| 业务闭环 | 无 | 预测「参与→开奖→结算→奖励→流水」全链路用例；至少 5 条跨模块关联用例 |
| 系统权限 | 0 | 安卓/iOS、PC-web、移动端-web 权限获取/拒绝/撤销用例 |
| 接口用例 | 2xx 冒烟 | 真实请求体/响应字段断言/正负向边界（本批先重构结构 + 高优先接口深补，全量接口深补列入后续批次） |
| 来源可溯 | requirement_module=0 | 每条用例 source_doc 关联原型页或功能地图文档；`docs/体育平台-用例结构规范.md` 落库 |

## 3. 非目标（本次不做）

- **知识中心可用性修复**（图谱语义、实体来源、wiki 编译/对比结果展示、项目球去留）→ 批次 B。
- **需求/设计稿正式入库平台**（上传→提取→确认→生成，解决截图缺失/导入为 0）→ 批次 C（本批直接读取本地原型 HTML/图片作为用例输入，不依赖平台入库链路）。
- **全量接口用例深补**：本批完成接口用例结构拆分 + 预测/赛事详情等核心接口真实请求体/断言深补；其余接口深补列入批次 D。
- **UI 自动化脚本落地**：本批只产出用例与结构，UI 自动化映射后续批次。
- 运营后台生产账号登录（生产账号不公开，沿用测试环境 `camel-admintest5` + 需求原型为准）。
- 平台自身系统管理模块（日志/账号/角色/菜单/版本更新）不在体育用例范围。

## 4. 用户故事 + 验收标准

- As a **资深测试工程师**, I want 每个模块按「入口/一级/二级」拆分且功能/接口分离，so that 用例能按端与后台定位、可直接执行。
- As a **测试负责人**, I want 每个模块覆盖状态机/异常/用户闭环/关联模块，so that 用例不是孤立的「样子货」而是可用的生产级用例。
- As a **测试执行者**, I want 用例有前置数据构造、明确步骤与预期、可追溯到需求原型页，so that 无需求上下文也能执行与验收。
- As a **平台承接方**, I want 覆盖到需求文档之外、生产实际存在的模块（弹幕/聊天/数据/个人中心等），so that 面向百万用户的平台没有遗漏。

验收标准（Given/When/Then）：
- Given 用例库重构后，When 按 domain 过滤，Then 功能用例与接口用例互不混排，且用户端可再按 4 入口过滤、后台可按 konfi/运营后台过滤。
- Given Pick/预测模块，When 逐条核对需求原型 `预测.html` 的功能点与异常处理，Then 每条规则均有对应用例（含无预测/预测已截止/比赛进行中预测已结束/「?」帮助/参与状态/预测历史/预测更多比赛/下注成功/结算/奖励发放/三选项全下注）。
- Given 联赛/球队/球员页面，When 逐 Tab 核对原型与生产，Then 每个 Tab 的内容、空态、无数据源、跳转均有用例。
- Given 任一核心用户流程，When 走完闭环，Then 存在跨模块关联用例（如 下注→开奖→结算→银钻流水→我的资产）。

## 5. 技术考量

- **用例载体**：平台 `test_case`（domain/module/tags/preconditions/steps/expected_result/api_*）。结构改造通过「新增规范域 + 批量导入脚本」实现，不动既有域数据（保留审计）。
- **输入源**（均为本地已有材料）：
  - 需求原型：`test-platform-v2/backend/data/axure_extract_test/`（130+ HTML，含「功能点|说明」表）+ `axure_extract_61930a83`（运营后台 70+ 页）+ `axure_extract_08b1a2b5/3989c196`（活动）+ 各 `images/` 设计稿。
  - 生产勘察：`work-logs/evidence/batch-110/production-walkthrough-v2/`（40 页文本/JSON）、`vision-walkthrough/`（9 页识图）、`xhr-samples/`（34 接口真实样本）、`admin-walkthrough/nav.json`（15 个后台模块全菜单）、`konfi-inventory-sports.json`（konfi 配置表）。
  - 功能地图：`docs/体育平台-功能模块地图.md`（v2）。
- **结构**：新增域 `体育-用户端-功能` / `体育-运营后台-功能` / `体育-接口测试`；模块路径 `入口/一级模块/二级模块`（入口=安卓iOS/PC-web/移动端-web/运营后台/konfi）；tags 记录 功能/接口、优先级、闭环/关联标记。
- **风险**：全模块深度用例量大，按模块组分批切片交付；本批覆盖「全模块结构 + 高价值模块深度用例」，剩余模块深度用例在批次内滚动补齐（以 kanban 追踪）。
- **工具**：新增 `scripts/sports/` 用例结构校验与导入脚本（可重复执行、幂等）。
