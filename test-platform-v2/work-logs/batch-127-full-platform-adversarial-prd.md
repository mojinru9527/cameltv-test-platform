# Batch 127 — PRD（测试平台全功能第一性原理验收与对抗性加固）

> **Product (🟦)** | Date: 2026-08-09 | Status: Approved for implementation | Mode: full

## 1. 问题陈述

测试平台已经覆盖需求、用例、计划、API/UI 自动化、知识中心、发布批次和系统管理等大量能力，但“路由能打开”不等于“功能可用”。本批从第一性原理重新定义平台价值：用户必须能发现能力、理解状态、完成关键任务、相信统计、在失败时知道如何恢复，并且不会因数据规模、权限或外部依赖得到空白页或误导结果。

生产只读走查已确认核心模块基本可访问，同时暴露出以下系统性风险：

- 同一批用例在工作台与用例服务使用不同口径，`1579` 总数与 `1011 + 602` 类型数无法守恒。
- 需求页首次进入可能长时间空白；交互缺口计算对 2217 条边和用例做重复文本拼接与逐对扫描。
- 知识概览、图谱、实体页的总量口径不一致；实体页把 200 条加载上限当成全量统计。
- 多个知识状态直接展示 `pending / approved / active / parsed`，破坏中文语义和状态可信度。
- 运维发布控制在未配置时暴露内部存储错误；部分重要能力仅能靠直达 URL 发现。
- 页面标题与主标题术语漂移，UI 自动化与调度存在未命名控件，性能页缺少文档标题。
- 现有“全平台”E2E 主要验证路由可达，未覆盖新增路由、页签、动态详情和本地 CRUD 主流程。
- 文档仍声称生产未部署或不存在运维路由，与真实产品状态不符。

## 2. 目标与成功指标

| 维度 | 基线 | 本批目标 | 验收方式 |
|------|------|----------|----------|
| 功能覆盖 | 旧 E2E 以路由可达为主 | 公开入口、29 个受保护页面、动态详情、核心页签、读写主流程均进入矩阵 | Batch 127 用例矩阵 + Playwright 证据 |

## 3. 用户故事与验收标准

### US-1：可信统计

作为测试负责人，我希望工作台和用例服务对功能/API/UI 用例采用同一口径，以便我能用这些数字做覆盖与资源决策。

- Given 同一项目同时存在 `manual`、历史 `functional`、`api`、`ui` 和软删除用例，When 查询工作台与用例统计，Then 历史 `functional` 归入功能用例、软删除排除、各类型之和等于总数。
- Given 用户选择“功能用例”，When 加载列表，Then 同时返回 `manual` 与历史 `functional`，且页签数字来自类型统计而不是业务域猜测。

### US-2：可感知且可扩展的需求覆盖

作为需求评审者，我希望进入需求页立即看到加载反馈，并在大量交互边时仍能得到相同覆盖结果。

- Given 2217 条拓扑边和数百条用例，When 计算缺口，Then 可搜索用例语料只准备一次，返回结果与原算法一致。
- Given 请求尚未完成，When 用户进入需求页，Then 首屏不是无反馈空白。

### US-3：可信知识资产

作为知识中心用户，我希望“当前加载条数”和“项目全量”被清楚区分，并看到本地化状态。

- Given 项目有超过 200 个实体，When 打开实体页，Then 页头显示服务端全量分类统计，列表明确当前展示上限/筛选结果。
- Given 产物、Wiki 和原始来源处于任一已知状态，When 渲染状态，Then 显示中文标签和语义色；未知状态使用中性回退。
- Given 实体缺来源或置信度为 0，When 查看列表，Then 页面明确标记数据质量问题而不伪造来源或置信度。

### US-4：受控降级与可发现性

作为平台管理员，我希望外部能力未配置时得到产品化说明，而不是内部异常文本；核心能力能从信息架构中被发现。

- Given release-control store 未配置，When 打开运维发布控制，Then 显示“当前环境未启用”说明和恢复条件，不显示内部异常。
- Given 路由存在但菜单未开放，When 完成评审，Then 每个隐藏入口都有明确的产品状态：正式入口、受控实验、仅开发或退役，记录在本批报告。

### US-5：可回归的全功能主流程

作为 QA，我希望自动化覆盖“打开、查看、筛选、创建、编辑、删除、失败恢复”而非只检查标题。

- Given 生产已登录会话，When 执行生产套件，Then 仅做只读导航/筛选/详情/页签验证，不写入生产数据。
- Given 隔离本地数据库，When 执行本地主流程，Then 项目、需求、用例、计划、调度、缺陷、数据集等可逆 CRUD 通过，并清理本批数据。
- Given 无权限、错误输入、空数据或外部依赖不可用，When 触发对应路径，Then 展示可理解的拒绝/错误/空态且无白屏。

## 4. 范围

### 功能域

- 认证：登录、注册、修改密码、受保护路由。
- 租户与项目：我的项目、组织、项目管理与项目上下文切换。
- 核心测试链路：工作台、质量追溯、需求、需求评审、用例、脑图、计划、计划详情。
- 自动化：API 测试、UI 自动化、Playground、性能测试、蓝湖证据。
- 质量运营：专项测试、调度、缺陷、报告、通知、环境变量、数据集、集成配置。
- 知识与智能：知识中心 12 页签、Agent 工作台。
- 交付治理：发布批次、批次详情、全景、运维发布控制。
- 平台管理：系统管理、主题实验室、404/异常边界。

### 非目标

- 不在生产执行创建、更新、删除、审批、导入、发布或回滚。
- 不伪造 C126-1 的实体来源，不虚构 C126-3 的置信度。
- 不解决依赖 iOS 设备、Test5 VPN、生产部署凭据等外部阻塞项。
- 不把所有历史 P3 债务一次性重构；未完成项必须带证据进入 C 条件。

## 5. 约束与风险

- 生产走查必须只读；所有写路径在独立 worktree、独立端口与隔离数据库执行。
- 新增静态 API 路由必须注册在 `/{id}` 动态路由前，避免 422 抢路由。
- React 异步请求必须支持卸载清理；Tab 非激活内容不得被 `forceMount`。
- 统计修复必须兼容历史 `functional` 数据，不可通过前端加减数字掩盖后端口径。
- 任何 C 条件必须同步追踪器；Blocked 不得记为 Pass。

## 6. 上线与回滚

| 阶段 | 门槛 |
|------|------|
| 本地实现 | 定向测试先红后绿；production read-only 与 local CRUD 证据齐备 |
| QA | 后端 F821/相关/全量 pytest；前端 typecheck/build/相关/全量 Vitest；E2E 与两项审计 |
| Draft PR | 用户一次总确认后 push；基础 `audit-ai-pr` 通过 |
| 合入 | required checks 全绿；最终审计；Leader APPROVED；squash merge main |
| 回滚 | 通过 PR revert；统计/接口改动保持向后兼容，不执行不可逆生产迁移 |
