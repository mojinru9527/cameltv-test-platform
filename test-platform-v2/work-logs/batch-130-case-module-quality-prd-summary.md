# Batch 130 — PRD Summary（用例模块聚合与异常覆盖加固）
> **Product (🟦)** | Date: 2026-08-09 | Status: Approved | mode: full

## 1. 问题陈述

### 1.1 分类树把测试维度误当成业务模块

1. 当前用例服务采用 `界面 → 原始 domain → 原始 module path`，因此 `体育-用户端-功能`、`体育平台-用户端` 等技术域会重复出现在业务模块外层。
2. Batch 122 曾把 `安卓iOS / PC-web / 移动端-web` 作为 module path 首段；这些是同一功能的覆盖维度，不是三个业务模块。按终端拆树会把同一功能的用例分散，用户无法一次看到该功能的完整风险集。
3. 正确结构应为 `用户端/运营后台/接口测试 → 业务一级模块 → 业务子模块`。终端差异继续保留在标签和用例正文中，不能因聚合而丢失。

### 1.2 生产仍在使用小规模旧资产

1. 当前仓库全量资产为 7,559 条基础用例 + 244 条深度用例；基础用例中 3,099 条负向、668 条边界，非 happy-path 占 49.8%。
2. 生产所见约 977 条主要来自旧批次，C125-3 的全量导入尚未闭环，因此抽查时仍以单步正常用例为主。
3. 现有 `import_sports_cases.py` 有两处阻断：基础 `TC-xxx` 在各模块内重复却使用统一前缀；查重传入 API 未实现的 `case_id` 参数，项目已有任意用例时可能误把后续记录全部判为已存在。

### 1.3 有负向数量不等于有对抗深度

全量资产已经覆盖空态、权限和输入边界，但多个模块缺少上游失败后的恢复、快速重复操作、并发写入、幂等与事务副作用校验。异常用例还埋在列表中，缺少直接筛选和质量门禁。

## 2. 成功指标

| 指标 | 基线 | 目标 | 证据 |
|------|------|------|------|
| 分类主轴 | 原始 domain + 终端壳层 | 只展示界面与真实业务模块；规范化节点中 PC/Web/安卓/iOS 壳层为 0 | 后端 taxonomy 测试 + 数据审计 |
| 同功能聚合 | PC、移动 Web、App 分散 | 同一业务模块聚合；终端保存在 `端:*` 标签/正文 | API 响应 + UI 走查 |
| 分类筛选 | 树节点展示值与精确存储值耦合 | 规范化域/路径可筛出所有原始别名与终端变体，计数守恒 | 列表/树契约测试 |
| 全量导入 | C125-3 未闭环；编号/查重缺陷 | 7,803 条资产均获稳定唯一 ID；查重精确；重复执行 created=0 | dry-run/模拟 API 测试 + 审计报告 |
| 正负覆盖 | 基础非 happy-path 49.8%，深度 244 条缺分类元数据 | 38/38 业务模块至少有正向+负向；深度用例元数据完整 | 质量审计脚本 |
| 对抗场景 | 故障恢复/重复并发分布不均 | 38/38 模块具备适用的故障恢复与重复/并发用例；预期包含 UI、数据和副作用断言 | Batch 130 overlay + 审计 |
| 异常可发现性 | 只能搜索标题或逐条打开 | 用例服务支持正向/负向/边界筛选并在表格显示场景标签 | 前端测试 + 浏览器证据 |

## 4. 用户故事与验收标准

### US1：按业务模块查看完整用例

- As a 测试人员, I want 在“用户端/运营后台”下直接看到首页、赛事详情、UGC、财务管理等真实业务模块, so that 同一功能的全部用例集中可查。
- Given `体育-用户端-功能 + 赛事详情/预测Pick`、`用户端/赛事详情/赛事详情页(PC)` 等历史变体 / When 请求 taxonomy / Then 均聚合到 `用户端 → 赛事详情`，且节点计数等于对应原始用例总数。
- Given 选择 `赛事详情` 或其子模块 / When 请求列表 / Then 返回所有原始 domain/module 别名下的匹配用例，而非只匹配一个存储字符串。

### US2：保留终端差异但不拆散模块

- As a 测试负责人, I want Android/iOS、PC Web、移动 Web 仍可在用例中追溯, so that 聚合不会造成端差异漏测。
- Given 一条适用于三个用户入口的用例 / When 导入 / Then 仅产生一个业务用例记录，tags 含三个 `端:*` 标签；taxonomy 不生成三个终端节点。

### US3：直接审查异常场景

- As a 测试执行者, I want 按正向/负向/边界筛选, so that 可以独立评审异常覆盖。
- Given 默认功能用例列表 / When 选择“负向/异常” / Then API 仅返回 `positive_negative=negative`，列表显示“负向”标签；边界同理。

### US4：全量资产可安全、幂等导入

- As a 发布负责人, I want 每条基础用例有稳定唯一编号且查重精确, so that 可以重复运行导入而不漏导或重复。
- Given 两个模块都含 `TC-001` / When 生成 payload / Then `case_id` 不同且同一输入重跑保持不变。
- Given 项目已有无关用例 / When 检查目标 `case_id` / Then 不误判存在；仅完全相同 `case_id` 被跳过。

### US5：每个模块有可执行的对抗场景

- As a 资深测试工程师, I want 所有 38 个业务模块至少覆盖故障恢复和重复/并发风险, so that 不只验证正常展示与空态。
- 每条补充用例必须写明故障注入/操作输入、可观察 UI 结果、数据/计数/流水/审计副作用，以及恢复或重试后的最终状态；禁止只写“提示正确”“系统正常”。

## 5. 技术与上线考量

- 规范化为响应与筛选层的确定性函数，不迁移或破坏历史 `domain/module` 审计值。
- 列表新增规范化筛选时先按项目/类型等 SQL 条件缩小集合，再计算匹配 ID，保持分页与 total 一致。
- 导入时写入稳定规范位置（如 `用户端/赛事详情`），并把终端范围写入 tags；旧数据由同一规范化函数兼容。
- Batch 130 adversarial overlay 是可审计静态资产，由脚本合并；质量审计失败即阻断导入。
- 本地、PR、部署、生产导入分层执行；合入 main 不等于立即写生产数据。
