# Batch 130 — Retrospective

> Date: 2026-08-09 | Mode: full | Executor: codex

## What worked

- 把终端从业务树降为标签，使 PC Web、安卓/iOS、移动 Web 的差异可追溯，同时不重复真实功能模块。
- 以 7,879 条完整资产做质量门禁，而不是根据页面抽样推断覆盖；数量、必填字段、唯一 ID 和模块配对都可复现。
- 把异常场景拆成模块级故障恢复与重复/并发，断言业务不变量和副作用，避免只替换“成功/失败”标题。
- API、列表、taxonomy、导出和 UI 共用规范过滤语义，减少同一分类在多端漂移。

## What was adversarially challenged

- 裸“商城”和“UGC”同时存在于用户端与后台，名称集合无法可靠判端；最终以 consolidated 来源模块锁定权威上层，并新增全量错配门禁。
- 旧导入器把各文件重复的 `TC-001` 当作全局 ID，还可能把未过滤接口返回的 total 当作命中；改为稳定命名空间 ID 和精确响应 ID 检查。
- 总体非 happy-path 比例不低不代表关键模块不漏测；最终要求 38/38 模块正负向成对，并逐模块具备两类对抗场景。
- 分类器抽到新模块后，旧代码仍从 service 导入函数；最终保留兼容重导出并以全量回归证明没有破坏既有调用者。

## Reusable lessons

1. 功能分类的权威来源应是产品模块清单；终端、技术栈和历史文件名只能作为元数据。
2. “异常覆盖率”至少同时检查总体比例、逐模块配对和具体风险类别，三者不可互相替代。
3. 批量导入的幂等性必须基于稳定全局 ID 的精确命中，不能依赖分页 total 或局部编号。
4. 规范化迁移应保留兼容读取路径，同时让新导入数据直接写入规范结构，逐步减少运行时猜测。

## Follow-up

- 合入并进入发布窗口后，执行完整生产 dry-run、受控导入和线上 7,879 条计数/分类复验；本地交付不伪造生产完成状态。
- 用例规模显著超过当前量级时，评估把规范 surface/domain/module 持久化并建立索引。
- 不新增新的 C 条件；C125-3 的代码与数据准备已完成，生产执行仍按原外部解除条件跟踪。
