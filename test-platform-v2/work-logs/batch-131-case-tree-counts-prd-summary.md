## 1. 问题陈述

用例服务的父模块计数包含“直接归属于当前模块、未填写下一层子模块”的用例，但模块树只展示有子模块路径的节点。生产截图中 `FAQ帮助 (27)` 的四个可见子级合计仅为 `5 + 2 + 1 + 1 = 9`，剩余 18 条没有可见核算项，用户会误以为统计错误或用例丢失。

根因位于展示语义：父节点总数是“本级直属 + 所有后代”，现有树只渲染后代。当本级直属数量大于 0 时，父子计数不守恒。

## 2. 成功指标

| 指标 | 基线 | 目标 | 测量窗口 |
|------|------|------|---------|
| 非叶父节点计数守恒 | FAQ帮助 27，子级合计 9 | 父级 = 直属用例 + 所有直接子级，27 = 18 + 9 | 本批验收 |
| 错误筛选请求 | 直属数量不可见 | 直属统计项不触发伪造 taxonomy_module 筛选 | 本批验收 |
| 回归 | 未覆盖直属计数 | Vitest 覆盖差值、0 差值、异常负差值保护 | 本批验收 |

## 4. 用户故事与验收标准

- As a 测试平台用户, I want 每个展开模块的数量能够在可见子项中完整对账, so that 我能确认用例没有漏展示或重复统计。
- Given 父节点有真实子节点且存在直属用例 / When 展开父节点 / Then 首个说明项显示 `直属用例 (差值)`，父级数量等于它与直接子级数量之和。
- Given 父节点没有直属用例 / When 展开父节点 / Then 不显示 0 数量说明项。
- Given 后端异常返回子级合计大于父级 / When 构建树 / Then 直属数量按 0 处理，不显示负数。
- Given 用户点击模块树 / When 点击真实节点 / Then 原筛选逻辑不变；直属统计项不可点击且不发送请求。

## 5. 技术考量

- 前端根据 `parent.count - sum(immediate child.count)` 推导直属数量，使用后端已有聚合计数，不新增网络请求，避免 N+1。
- 直属统计项使用非交互展示，防止把统计说明误当成真实 taxonomy_module。
- 递归处理业务域和任意层模块节点，保证所有非叶父节点遵守同一守恒规则。
