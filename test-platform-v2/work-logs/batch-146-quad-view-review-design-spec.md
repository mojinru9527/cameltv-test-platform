# Batch 146 — Design 规范（四视角对抗审查方法与 xmind 结构）

> **Design (🎨)** | Date: 2026-08-11 | 本批无代码交付，本规范定义审查方法与产出物结构，确保四视角可执行、可复核、可汇总。

## 1. 审查执行规范（对抗性深度，非浅层）

### 1.1 通用操作基线（每个模块必须执行，缺项要注明原因）

| 类别 | 操作 | 核查点 |
|------|------|--------|
| 读 | 列表加载 | 首屏加载态、时长、分页、排序、筛选、搜索 |
| 读 | 详情 | 字段完整性、关联跳转、回退、深链接 |
| 写 | 创建 | 表单校验、必填、边界、重复提交、成功反馈、创建后跳转 |
| 写 | 编辑 | 回填正确性、保存反馈、并发修改 |
| 写 | 删除 | 确认交互、级联影响、误删保护、删除后列表刷新 |
| 错 | 错误路径 | 非法输入、无权限、外部依赖挂、网络失败提示 |
| 空 | 空态/边界 | 无数据态文案、0 结果、超长文本、特殊字符 |
| 性 | 网络 | 重复请求、N+1、冗余拉取、缓存缺失、未清理请求 |

### 1.2 五维评分（每模块 1–5 分）

| 维度 | 含义 |
|------|------|
| 功能完整 | 功能点是否齐备、是否真实可用（非占位） |
| 易用性 | 学习成本、任务完成路径长度、操作反馈 |
| 一致性 | 与平台其他模块的交互/视觉/文案一致性 |
| 性能 | 首屏、交互响应、大数据量 |
| 价值密度 | 对测试团队真实效率的提升（冗余度越低越高） |

### 1.3 缺陷定级（沿用团队 P0–P3）

- **P0**：阻断核心任务/数据错误/安全风险
- **P1**：严重功能缺陷或体验断裂（有绕行但成本高）
- **P2**：一般缺陷/明显不一致/低效
- **P3**：细节打磨/增强建议

### 1.4 证据要求

- 每个问题：截图（`evidence/batch-146/` 按视角/模块分目录）+ 复现步骤 + 影响面
- 每个页面域至少 1 张全屏截图；深色模式关键页各 1 张
- Network 捕获：全会话 HAR 摘要 + 重复请求对照表

## 2. 四视角审查框架（本批核心，跳出 batch-127 路由可达框架）

### 2.1 视角1：资深 UI 设计工程师（对抗性）

审查清单：布局与栅格、间距节奏、层级与焦点、文字可读性（字号/对比度/WCAG）、颜色语义（状态色/主题一致性）、组件规范符合度（对照 `cameltv-ui-conventions`）、交互反馈（hover/active/loading/disabled）、表单可用性（label/校验时机/错误展示）、弹窗/抽屉/表格密度、空态/加载态/骨架屏、深色模式、响应式（桌面/平板/手机）、动效合理性、图标与文案一致性、可访问性（键盘/焦点/ARIA）。

### 2.2 视角2：资深测试工程师（体育项目适配）

- 功能测试模块：用真实体育项目（7559+ 用例）跑通 用例管理全流程（增删改查/导入导出/筛选/脑图/计划关联）；评估用例结构对体育业务的适配度。
- 接口测试模块：真实接口用例（170+）执行/批量执行/断言/依赖链/定时任务；评估参数构造、环境切换、结果回填。
- UI 自动化模块：真实 job 运行、报告解读、失败排查。
- 输出：①不适配清单（功能与体育业务冲突/无法使用的）；②冗余清单（没人会用的功能/重复入口/无效开关）；③提效建议（用例-功能-接口-UI 自动化四者如何关联，输入输出如何互哺）。
- 特别核查：P0 用例口径（C110-4）、覆盖率（C126-2）、接口关联（C107-2 场景串联）。

### 2.3 视角3：资深架构师

- 架构分层梳理：前端（React 18+ Vite + shadcn/Radix）→ API 层（fetch hooks）→ 后端（FastAPI 模块化）→ 存储（PostgreSQL/Redis/Qdrant?）→ 外部（Railway/Vercel/蓝湖/LLM）。
- 模块关联矩阵：24 页面域 ↔ 38 API 模块 ↔ 数据表 ↔ 外部依赖，识别环形依赖、单点、重复实现。
- **前后端请求冗余专项**：从代码层找重复请求模式（多 hook 拉同一数据、列表+详情重复拉取、轮询无退避、组件重复挂载、Tabs forceMount、context 重复 fetch）；生产 Network 实证。
- 空白机搭建流程（Windows/mac）：从仓库文档+脚本梳理 30 步流程，标注可优化项与冗余项（依赖、工具链、手动步骤）。
- 输出：架构问题清单 + 优化优先级。

### 2.4 视角4：甲方交付验收（功能流转）

- 以「甲方验收测试平台交付」立场：逐模块梳理功能流转（用户→操作→系统→数据→下一环节），标注流转断裂点、手工环节、黑盒环节。
- 与交付文档（`测试平台使用手册.md`、`现状功能PRD.md`）对照，找「文档说有/实际没有」「实际有/文档没写」。
- 输出：功能流转清单 + 不符合预期项 + 优化建议。

## 3. xmind 结构设计（交付物）

文件名：`docs/平台功能流转与数据流转-四视角审查.xmind`（同时输出 `.xmind` 与 JSON 源）

```
平台功能流转与数据流转
├── 0 总览：五条主线（需求→用例→执行→缺陷→报告；资产→知识；发布→运维）
├── 1 需求域（需求/评审/模块树/生产差异）— 功能流转 + 数据流转 + 问题标注
├── 2 用例域（用例/脑图/计划）— 同上
├── 3 执行域（API 测试/UI 自动化/专项/调度/性能）
├── 4 质量域（缺陷/报告/追溯/数据集/环境/集成/通知）
├── 5 资产域（蓝湖证据/知识中心/Agent/图谱）
├── 6 交付域（发布批次/全景/运维控制）
├── 7 平台域（系统/组织/项目/主题）
└── 8 问题热力图（按模块 P0–P3 计数标注）
```

每个节点携带：功能描述、前置/后置模块、数据实体、API 端点、问题标签（P0–P3 + 视角归属）。
