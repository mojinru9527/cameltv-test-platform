## 0. 背景：为什么弃用 Batch 127 框架

Batch 127（`batch-127-full-platform-adversarial-review`，2026-08-09）以「路由可达 + 统计口径 + 状态本地化 + 加载态/降级体验 + a11y 定向」为框架，报告仅 ~60 行；Batch 126 为 24 导航模块只读走查 + 数据核对。两者均为**单视角、浅层、以「页面能开/数字守恒」为验收**，未回答以下问题：

- 每个功能对真实测试团队效率有没有提升？哪些功能不适应体育项目真实业务？
- 用例/功能/接口/UI 自动化四者之间如何关联才高效？
- 前端是否存在重复/冗余 API 请求（用户点名）？
- 空白 Windows/mac 搭建整套平台的真实成本与冗余？
- 甲方视角的功能流转是否符合交付预期？

**本批跳出旧框架**：不预设「路由能开=功能可用」，以四类专业角色的对抗性使用 + 全链路数据流转梳理为主线。

## 1. 问题陈述

测试平台已交付 24+ 页面域 / 38 后端 API 模块 / 31 路由，且已导入体育平台真实业务（7559+ 基础用例、170+ 接口用例、925 实体图谱、33 域功能用例）。但缺乏一次**跨角色、跨模块、深到 CRUD 细节**的对抗性审查：UI 是否经得起资深 UI 工程师挑剔、测试模块是否真正适配体育项目、架构与请求链路是否冗余、甲方验收是否满意功能流转。

## 4. 范围

### 覆盖模块（前端 24 页面域 = 后端 38 API 模块）

登录/注册/改密 → 项目/组织/我的项目 → 工作台/追溯/需求/需求评审 → 用例/脑图/计划 → API 测试/UI 自动化/专项/调度/缺陷/报告 → 系统/通知/环境/数据集/集成 → 知识中心/Agent 工作台 → Playground/性能 → 蓝湖证据/发布批次/运维控制。

### 审查方法（对抗性，非浅层）

- 每个模块执行「列表-详情-筛选-分页-创建-编辑-删除-错误路径-空态-边界」至少 10 项操作核查；只读页面核查加载/空态/排序/搜索。
- 生产网络面板全程记录：重复请求、N+1、冗余拉取、未缓存。
- 每视角截图证据 ≥8 张/域，问题截图入 `work-logs/evidence/batch-146/`。
- 评分：每个模块按五维（功能完整/易用性/一致性/性能/价值密度）1–5 分，跨视角汇总。

### 非目标

- 不修复代码（用户确认仅报告+xmind）。
- 不做测试环境/本地部署验证（纯生产审查；空白机流程基于代码与文档静态梳理 + 仓库证据）。
- 不处理外部阻塞项（iOS 真机、Test5 VPN、lanhu 凭证）。
