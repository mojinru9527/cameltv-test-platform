## 3. 关键问题：用例-功能-接口-UI 自动化四者关联断裂（P0 根因分析）

### 3.1 现状数据链（实测）

```
需求文档(5) → AI 导入用例 476 → 功能用例 7845（域/模块标注）→ 测试计划 325（仅接口用例！）
                                              ↘ 接口用例 34（样本级）↗     ↓ 一键执行
UI 自动化 job(2) ← 无用例映射                  ← 执行 325/325 失败 → 执行历史(325) → 报告 0
                                                                        ↓
                                                                  缺陷 0（无自动转缺陷）
```

### 3.2 断裂点

1. **计划只有接口用例**：325 条全为 OpenAPI 导入生成的接口用例，功能用例（7845）完全没有进计划——「功能用例 → 计划 → 执行」主链路空转
2. **接口执行不回流功能用例**：接口用例执行结果不更新功能用例状态，功能用例 7845 永远「草稿」态
3. **UI 自动化与用例库零关联**：2 个 job 的 spec 与用例库无映射字段，用例变更无法驱动回归范围
4. **执行失败无下游动作**：325 失败 → 无缺陷、无报告、无通知；失败分诊需手动触发 AI 且置信度 0%
5. **统计口径断裂**：工作台 7879 vs 追溯 9424 vs 集成页 7879 三套数字并存

### 3.3 四者高效关联方案（建议）

```
功能用例(域/模块/P0 锚点)
   │ ① 用例↔自动化映射：P0 功能用例绑定 UI spec 或接口用例 ID（新增映射字段/表）
   │ ② 计划编排：计划同时纳入 功能用例(人工/半自动) + 接口用例(自动) + UI job
   ↓
测试计划执行
   │ ③ 结果回填：接口/UI 执行结果自动回填功能用例状态（通过/失败/阻塞）
   │ ④ 失败自动分诊：失败执行 → 自动打缺陷草稿（标题=用例+环境+时间）+ 通知
   ↓
报告(自动生成) + 追溯(单一口径) + 工作台(执行统计真实化)
   │ ⑤ 覆盖率：以「计划覆盖率」为唯一口径，去掉 4 套统计实现（见架构报告）
   ↓
回归范围推导：需求变更 → 关联用例 → 关联计划 → 定向回归
```

**预期收益**：缺陷从「0 手动」→ 自动录入；覆盖率从「3 套数字」→ 1 套可信；回归从「全量盲跑」→ 需求驱动定向；UI 自动化从「2 条固定 spec」→ 用例映射驱动。
