## 1. 问题陈述

Batch 172 接入 DeepSeek Harness（DSH）执行能力，Leader 登记两项 P1 安全条件未闭环：

1. **C172-2 凭据并发覆盖**：`dsh_runner._run_python_sdk`（:233-245）通过改 `os.environ` 传递 DEEPSEEK_API_KEY 等凭据给 SDK，多线程并发任务会互相覆盖（A 线程写入、B 线程覆盖、A 读到错误凭据）。node 运行时走子进程 env（天然隔离），**python-sdk 生产路径存在并发凭据泄漏/错配风险**。
2. **C172-1 沙箱未加固**：生产启用 DSH 前需完成：
   - 工作区隔离：`_workspace_for` 在配置 `DSH_WORKSPACE` 时返回**共享目录**（多任务同目录写文件，任务间可互相读取/覆盖）；
   - 任务级配额：无并发上限（DshTask worker ThreadPool 2 但无全局闸门）、无任务文本长度上限、无凭据最小化保障；
   - 安全回归证据缺失。
   - 未加固前生产 `DSH_ENABLED` 必须保持 false（本批不改变该默认）。

## 3. 用户故事与验收

### US-1（C172-2）并发凭据隔离
> 作为平台运维，我希望并行 DSH 任务各自使用正确凭据，不因并发互相污染。

- **Given** 两个 python-sdk 任务并发执行（不同 project）
- **When** 均触发 DSH
- **Then** 每个任务使用自己的凭据组合（API key/base URL/model），测试断言两次执行的 env 快照互不交叉、结束后环境恢复

### US-2（C172-1）受限工作区 + 配额
> 作为安全审计者，我希望每个 DSH 任务在独立工作区运行且有资源上限，越界即失败。

- **Given** DSH_WORKSPACE 配置为共享根目录
- **When** 提交任务
- **Then** 任务在 `{根}/ws-{uuid}` 独立子目录执行；并发超过上限的任务排队/拒绝（可配置）
- **And** 任务文本超长被拒绝（可配置上限）；执行超时被强制终止（已有，回归覆盖）

### US-3 安全回归
> 作为 QA，我希望安全行为有自动化证据，防回归。

- **Given** test_dsh_sandbox.py
- **When** CI 运行
- **Then** 4 组测试全绿；node 运行时行为不受影响（既有测试全绿）

## 6. 风险

| 风险 | 缓解 |
|------|------|
| python-sdk 加锁序列化降低并发 | 锁粒度=env 突变+run 段；默认 DSH_MAX_CONCURRENT=1（安全优先），可配置上调；node 路径不受影响 |
| SDK 不支持显式凭据传参 | 锁方案兜底；测试证明隔离语义 |
| 工作区隔离破坏既有任务数据路径 | 现有任务均未显式用共享工作区（仅配置项）；隔离子目录向下兼容（根路径不变） |
