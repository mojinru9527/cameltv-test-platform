# Batch 64 — PRD Summary（架构解析与仓库拆分基线）

> **Product (🟦)** | Date: 2026-08-02 | Status: Approved

## 1. 问题陈述

用户（产品负责人）明确提出三项长期诉求，且均为当前单仓结构无法直接支撑的：

1. **仓库分离**：后续希望「前端仓库 / 后端仓库 / 运维平台」三仓独立，某些版本只做前端、某些版本只做后端，方便管理与发布；版本发布/分支发布直接通过运维平台执行。
2. **V1 退役**：`test-platform/`（V1）已被 V2 取代且已弃用；只有当 V2 完整覆盖 V1 对应功能时才允许移除 V1 代码。
3. **生产交付**：前几个版本已提交生产域名、服务器、数据库等地址；需要整理成可交付客户的清单，并发布到生产环境。

现状证据：
- 仓库同时存在 `test-platform/`（V1 单体，11 件 CLI 工具 + server + web-ui）与 `test-platform-v2/`（FastAPI + React 主力），V1 仍占据约 1/5 的仓库体积与维护注意力（见 `docs/repo-map.md` §2.2）。
- 前后端目前只是「目录级物理分离」（ADR-0003），不是仓库级分离：`backend/` 与 `frontend/` 共用一个 Git 仓库、同一版本号、同一 PR/CI 生命周期，无法按用户期望的「前端版本 / 后端版本」独立排期。
- 运维发布控制面已有事实层（`deploy/release-control/`，Batch 62）与只读展示页（`/operations-release`），但尚无独立运维平台仓库与 Phase 2 API/UI（ADR-0015 仍为 proposed）。
- 生产域名/服务器/数据库信息散落在 `docs/测试平台全功能验收文档-环境链接与账号汇总.md`、`test-platform/config/environments/prod.yaml`、`test-platform-v2/deploy/`（Vercel/Supabase，Batch 58）等多处，没有统一的「客户交付清单」。
- 仓库内存在意外跟踪的临时文件（`pective pipeline — ...` 两个文件），说明根目录缺少机器可校验的边界约束。

## 3. 非目标（本次不做）

- **不做 API-only 能力 UI**（C63-1：Token/Playground/导入导出/追溯下钻 UI）：用户已明确 batch-64 优先做架构基线；UI 排期顺延 batch-65，列入 C64-4 跟踪，避免本批范围膨胀引入回归。
- **不做仓库物理拆分动作**：本批只产出拆分决策、边界事实源与路线图；实际拆仓（git subtree/filter-repo 迁移）为后续批次，拆仓必须逐批过 QA 与验收。
- **不删除 V1 任何代码**：即使矩阵判定「可退役」，删除也走独立审计批次（对齐《能力产品化决策清单》规则 3：移除死能力必须走独立审计批次）。
- **不新增业务 API/前端页面**：本批无 FastAPI/React 业务改动。
- **外部阻塞项继续豁免**（C63-2 口径）：Test5/VPN 六契约、AI/OCR/蓝湖凭据、旧 PG 快照、真机性能、云注册 C58、DevOps 基础设施——均无授权，禁止补登假证据。
- **不发布 production**：生产基础设施未就绪（ADR-0015 §4），本批只整理交付清单，不执行、不伪造 production 发布。

## 4. 用户故事 + 验收标准

- As a 平台负责人，I want 一份资深架构师视角的现状解析，so that 我能基于事实决策仓库拆分与 V1 退役顺序。
  - 验收：Given 本批报告 / When 逐项核对 V1 工具与 V2 模块 / Then 每项都有「已覆盖/部分/缺失」判定与证据路径。
- As a 开发/发布管理者，I want 前端、后端、运维平台的边界由机器可校验，so that 拆分时不会出现「无主路径」或跨仓耦合。
  - 验收：Given `repo-boundaries.json` + 校验脚本 / When 运行 `--check` 与 `--selftest` / Then 退出码 0 且输出覆盖统计；新增未声明路径会失败。
- As a 交付负责人，I want 一份完整生产交付清单，so that 我可以直接据此部署生产并交付客户。
  - 验收：Given 清单 / When 核对域名、服务器、数据库、账号槽位、网络条件 / Then 条目齐全且不含明文密码/Token。
- As a 项目成员，I want V2 全部现有功能在架构调整期间保持不变，so that 不会出现功能缺失。
  - 验收：Given 本批零业务代码改动 / When 执行后端全量回归与前端门禁 / Then 无新增失败。

## 5. 技术考量

- 依赖：Python 3.10+（校验脚本纯标准库，无新依赖）；不触碰 FastAPI/React 现有依赖。
- 已知风险：
  - V1 部分工具（mock/capture/apidiff/datafactory/logagg/envcheck/loadtest）在 V2 无等价实现 → 矩阵中明确标「缺失」，V1 整体移除必须等待逐项迁移或用户批准废弃。
  - 拆分过程中 `lanhu-mcp`（子模块）与 `tests/` 资产的归属需要先行定义 → 本批边界清单给出归属。
  - 生产地址中的真实密码/Token 已由 `.env`/`production.env` 管理且 gitignored → 交付清单只记录槽位与引用名。
- 待解决问题：DB/Redis/MQ 真实内网地址仍是 `10.x.x.x` 占位（`test-platform/config/environments/*.yaml`），需运维提供后回填清单。
