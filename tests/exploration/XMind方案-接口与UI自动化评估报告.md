## 一、XMind 方案实现逻辑梳理

### 1.1 主干 A：用例转换到 API 自动化用例

```
[手工用例] → [AI 泛化] → [API 自动化用例] → [批量执行] → [失败分析] → [脚本健壮性]
     ↑              ↑              ↑
[接口文档]      [编排 Demo]     [DDL]
[代码 diff]     [结果检查 skill]
```

**核心流程（5 步）：**

| 步骤 | 逻辑 | 关键机制 |
|------|------|----------|
| 1. 用例编写 | 用例要"适合 AI 泛化"：按被测系统表述、线形化表示执行步骤（先做什么后做什么）；**先输出一个详细的编排场景 Demo 用例给 AI**，按模块演进，完成后人工核查 | Demo 驱动（Few-shot） |
| 2. AI 编写脚本 | 写多个不同链路的 Demo（接口编排 + 断言：返回结果、数据源库/接口查询）；**AI 进行泛化 skill**：用手工用例 + 人工接口编排，泛化出某个模块的用例全集；配**结果检查 skill** 校验 | Skill 泛化 + 编排断言 |
| 3. 输入源 | **API 接口文档**：枚举差异 skill（与手工用例匹配/比较、补充手工用例）；**接口变动**：skill 修改接口字段（线索链：先找接口名称 → 再找影响的用例 → 按模块替换用例）；**功能变动**：diff 开发代码 → 对比自动化用例增删改 → 对比手工用例 → skill 同步修改自动化用例；**DDL**（数据库变更） | 接口文档 + 代码 diff 驱动 |
| 4. 转测后 | 批量执行用例 → **失败分析 skill**（优化手工用例、优化脚本、系统 bug 提审）→ 脚本健壮性验证（配置完善、参数化、全局 token、全局 mid 等自动配置） | 失败闭环 |
| 5. 剩余部分 | 完成 UI + 场景自动化剩余用例，需要人工完成验证（功能验证 + 非功能验证） | 人机分工 |

**注意事项（风险意识）：** 上下游接口依赖、跨团队数据依赖、第三方数据接入。

### 1.2 主干 B：UI 自动化

```
[手工用例(可被AI识别)] → [训练AI(模板/Demo)] → [AI参照用例+git代码写脚本] → [批量执行] → [AI分析结果]
                              ↑                        ↑
                    [页面模板/占位符]           [git代码(必要) + 需求/figma(辅助)]
```

**核心流程（4 步）：**

| 步骤 | 逻辑 | 关键机制 |
|------|------|----------|
| 1. 手工用例编写 | 用例要"可被 AI 识别"：确定到模块、界面控件、可操作步骤、界面的输入及输出条件、断言能识别界面具体元素/名称 | AI 可读用例规范 |
| 2. 训练 AI | **自定义页面模板**：写一个具体用例 Demo（公用字段 + 自定义字段 + 占位符，SKILL 模型和字段能力）；**多操作/切换页面场景用例**：完整的翻译/切换 Demo → skill 完成具体用例设计；**页面整个浏览/预览骨架**：页面跳转及功能流转；SKILL 本身约束/检查 | 模板 + Demo + 占位符 |
| 3. AI 参照手工用例写脚本 | **必要输入 = git 代码 + 用例**：git 代码按节奏提供（分析开发代码 skill；开发提供界面代码百分比 10%/30%/100%，时间点由测试与研发沟通）；根据 Demo 做脚本：界面性质断言 + 接口性质断言（无接口时：断言能力先行、断言接口占位符（URL 获取、参数获取），接口提供后 skill 刷新断言能力与结果）；**批量生成**：完整用例生成（skill 读取 git 代码，开发变动同步修改抹平差异：diff → 修改 → 线索（页面、组件名称等）→ 检查 skill）；回填补漏（全量回填替换所有占位符 / 增量回填，线索同上）；**辅助输入 = 需求、中央模块说明（自己/测试方案）、figma** | git 代码驱动 + 占位符 + diff 抹平 |
| 4. 执行与闭环 | 多进程、批量执行 → **AI 分析执行结果报告**：确认脚本 BUG（AI 给出修复建议及写错原因 → 继续批跑失败用例）/ 确认系统 BUG | AI 结果分析 |

## 三、差异对比（XMind 方案 vs 现有平台）

### 3.1 接口自动化对比

| 维度 | XMind 方案 | 现有平台 | 差异分析 |
|------|-----------|----------|----------|
| 用例生成驱动 | 手工用例 + Demo 编排 + AI 泛化 skill | 接口 schema + OpenAPI 导入 + 真实流量抓取 | 现有平台更"输入驱动"（文档/流量）；XMind 更"用例驱动"（手工用例为母本）。**两者互补：现有平台缺"手工用例泛化"路径** |
| 变更响应 | 接口变动/功能变动 skill（找接口名→找影响用例→按模块替换）+ diff 开发代码 | 重新导入 OpenAPI / 重新生成（无增量 diff 机制） | **XMind 的增量变更管理（diff→影响分析→定向修改）是显著优势**；现有平台变更后基本全量重来 |
| 断言 | 返回结果 + 数据源库/接口查询（可信任前提） | 8 类断言 + 响应结构断言 | XMind 增加了"数据源库/接口查询"级断言（更强）；现有平台断言类型更工程化 |

| 脚本健壮性 | 全局 token/全局 mid 自动配置、参数化 | 环境变量 + dataset 数据驱动 | 现有平台已有参数化；XMind 强调"自动配置"（mid=用户标识等体育特有概念） |
| DDL 输入 | 支持 DDL（数据库变更）作为输入 | 无 DDL 输入通道 | XMind 特有 |
| 人工介入 | 明确"剩余用例人工验证" | 全自动生成 | XMind 更务实 |

|------|-----------|----------|----------|

## 四、优缺点评估

### 4.1 XMind 方案优点

1. **变更驱动的增量维护**（接口 diff、代码 diff、DDL）→ 自动化脚本长期保鲜，这是现有平台最缺的
2. **用例驱动泛化**：手工用例 + Demo → AI 泛化模块用例全集，贴合测试团队"先有手工用例"的现实
3. **占位符机制**：接口未就绪时先做"断言能力 + 断言占位符"，接口提供后刷新 —— 前后端并行开发期友好
4. **失败双向闭环**：AI 分析结果不仅修脚本，还反向优化手工用例和提审系统 bug
5. **全局参数自动配置**（token/mid）、多进程、DDL 输入等细节务实
6. **人机分工明确**：剩余场景人工验证，不盲目追求 100% 自动化

### 4.2 XMind 方案缺点/风险

1. **🔴 UI 自动化强依赖 git 代码**：30%/100% 代码节奏、diff 抹平、页面/组件名称线索全部建立在代码可读上。**在当前"无法接入体育 git 仓库"的约束下，UI 自动化的核心机制（变更同步、完整生成、回填补漏）全部失效**
2. Skill 依赖较重：枚举差异、泛化、结果检查、失败分析等多个 skill 需要大量调优，冷启动成本高
3. Demo/模板训练依赖测试工程师先写出高质量编排 Demo（人工成本前置）
4. "数据源库/接口查询"断言依赖数据库可信与可访问（体育项目跨团队数据依赖风险）
5. 方案缺少执行平台化描述：报告、任务编排、权限、CI 集成等未提及（需要依托测试平台补）

### 4.3 现有平台优点

1. **工程化底座完整**：用例库、任务、报告、快照、CI、RBAC、缺陷、追溯全闭环
2. **接口自动化输入丰富**：OpenAPI/流量/真实样本三通道，8 类断言工程化
3. **UI 自动化不依赖代码**：midscene.js AI 视觉定位，**无 git 也能跑**
4. 失败分析已落地结构化诊断

### 4.4 现有平台缺点

1. **变更响应弱**：接口/功能变更后无 diff 增量维护机制，脚本易腐化（Batch 60 判 NEEDS WORK 的原因之一）
2. UI 自动化生产级未闭环：同步阻塞、脚本资产/环境/产物管理弱
3. 无 DDL 输入、无 figma 输入、无占位符先行机制
4. 用例生成偏"输入文档驱动"，缺少"手工用例泛化"路径

## 五、哪个更适配体育项目（结合 git 不可接入约束）

### 5.1 结论先行

| 维度 | 适配度 | 理由 |
|------|--------|------|
| **接口自动化** | **XMind 方案更适配**（但需落地到平台） | 接口自动化对 git 依赖低（主要靠接口文档/DDL/流量）；其增量变更维护、用例泛化、token/mid 全局参数化正好命中体育项目痛点；体育项目接口是微服务（account-service 等），接口文档/抓包可得 |
| **UI 自动化** | **现有平台方案更适配** | 🔴 XMind 的 UI 自动化核心机制（git 代码、diff、组件名称线索、全量回填）在**无法接入 git 的前提下不可行**；现有平台 midscene.js AI 语义/视觉定位不依赖代码，可对线上/测试环境直接跑 |

### 5.2 为什么接口自动化该学 XMind

- 体育项目**没有 git 权限 ≠ 没有接口文档**：线上实测已抓取 `api.cameltv.live`（匿名登录/广告配置/客户端配置），Swagger/流量可继续抓
- 体育项目**版本迭代快**（41 个版本、16.0.0 篮球新增）：接口变动频繁，XMind 的"接口文档枚举差异 skill → 找影响用例 → 按模块替换"正是高版本频次的刚需
- 体育项目有**全局 token/mid 体系**（线上已见匿名登录 key/value 会话）：XMind 的"全局 token、全局 mid 自动配置"直接对应
- 体育项目**跨团队/第三方数据依赖**（比分数据源、直播流、广告联盟）：XMind 已把"上下游接口依赖、第三方数据接入"列为注意事项，风险意识匹配

### 5.3 为什么 UI 自动化保持现有平台路线

- midscene.js 的 AI 定位能力**不需要 git 代码**，可对 camel1.tv 线上环境直接验证（我们已实测全站）
- 体育项目 UI 自动化最大障碍是**广告弹窗干扰**（赌博广告/popunder），需要的是流量拦截、popup 管理、多标签处理（现有探索方案已形成），而不是代码 diff
- 若未来 git 可接入，可**补充 XMind 的 diff 抹平机制作为增强**（而不是替换）

### 5.4 最终建议（融合路线）

```
┌─────────────────────────────────────────────────────────────┐
│  体育项目自动化推荐架构（git 不可接入约束下）                  │
├─────────────────────────────────────────────────────────────┤
│ 接口自动化：以现有平台为底座 + 吸收 XMind 三机制               │
│   ① 接口文档/流量/真实样本导入（已有）                        │
│   ② 新增：接口变更影响分析（diff 接口文档 → 找影响用例 → 替换）│
│   ③ 新增：全局 token/mid 自动配置（匿名登录会话复用）          │
│   ④ 新增：手工用例泛化 API 用例（Demo 驱动）                  │
├─────────────────────────────────────────────────────────────┤
│ UI 自动化：以现有 midscene.js 路线为主                        │
│   ① AI 语义定位（不依赖代码）✅ 已有                          │
│   ② 广告弹窗拦截/返回策略（探索已形成方案）                   │
│   ③ 未来 git 接入后：补充 diff 抹平机制作为增强               │
└─────────────────────────────────────────────────────────────┘
```
