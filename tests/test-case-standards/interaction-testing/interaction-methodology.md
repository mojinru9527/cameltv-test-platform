# 跨平台交互测试方法与准则

## 1. 目的与适用范围

本规范用于扩展功能测试用例，覆盖 Web、移动 Web、小程序、iOS/Android App、Windows/macOS/Linux 桌面客户端、PC 专用软件、触摸屏终端、遥控器交互设备、嵌入式/物联网设备及其他带人机交互的硬件。它不是所有产品都必须全部执行的固定清单；项目必须按实际平台、使用环境、用户角色和风险裁剪。

交互测试目标：用户能够发现功能、理解含义、正确操作、获得及时反馈、控制操作过程，并在错误/中断后恢复；系统在不同角色、平台、设备和环境下维持可预测行为。

| ISO 9241-210:2019 | 国际标准 | 以人为中心的设计过程 | 支持项目生命周期内理解用户、设计和评估 |

## 3. 通用交互准则（所有平台共用的检查主干）

### 3.1 可发现性与可供性
- 用户能否找到入口、识别可交互元素、理解触发方式。
- 图标是否有清楚语义；仅图标操作在必要时是否有名称/提示。
- 主要操作是否与次要操作有适当层级；危险操作是否不易误触。
- 不将颜色作为唯一状态信号。

### 3.2 自描述性与语义清晰
- 文案、单位、状态、错误原因、操作后果是否清楚。
- 相同概念是否使用一致名称；专业术语是否符合目标用户认知。
- 空状态是否解释为什么为空以及下一步能做什么。
- 用户是否能判断自己正在操作哪个对象、哪个版本或哪个范围。

### 3.3 状态可见与反馈完整
- 每个异步动作是否区分未开始、处理中、成功、失败、超时等适用状态。
- 反馈是否与真实后端结果一致，是否出现“提示成功但实际失败”。
- 长任务是否提供可理解进度/阶段；不可精确估计时不得伪造百分比。
- 反馈是否及时、不过度打断，也不会因一闪而难以感知。

### 3.4 一致性与可预测性
- 相同控件、相同动作、相同状态在不同页面/终端中是否保持一致。
- 返回、关闭、保存、取消、搜索、筛选、分页、排序是否遵循既定规则。
- 系统/平台约定与产品自定义行为有无冲突；差异是否有清晰说明。

### 3.5 用户控制与自由
- 是否可以取消、关闭、中止、返回、撤销或重做（按业务可行性）。
- 误进入流程是否有合理退出路径。
- 不可逆操作是否有足够确认、影响范围和恢复策略。
- 自动跳转、自动播放、自动提交、强制授权是否符合明确需求和平台要求。

### 3.6 错误预防与恢复
- 是否在输入前/提交前识别错误条件，减少无效操作。
- 错误是否指向具体字段/对象，说明原因和下一步。
- 错误发生后，已输入内容、已选对象、滚动位置和上下文是否按规则保留。
- 重试是否安全；重复点击是否会重复扣款、生成、创建、发布或提交。

### 3.7 导航与空间定位
- 用户能否理解当前位置、上一级、下一步、当前筛选条件和操作上下文。
- 返回/前进/关闭/面包屑/深链接/系统返回是否正确。
- 页面刷新、直接访问子路由、分享链接、登录跳转后是否保持上下文。
- 避免死路、循环跳转、无意离开和丢失未保存内容。

### 3.8 输入与操作适配
- 支持的输入方式是否都能完成核心任务：键盘、指针、触摸、手势、语音、遥控器、物理按键等。
- 输入法组合输入（IME）、粘贴、自动填充、扫码、拖放、文件选择是否适配实际场景。
- 单击/双击/长按/滑动/捏合等手势是否存在歧义和冲突。
- 硬件实体控件的方向、阻尼、按压行程、状态灯/声音/振动反馈是否符合设备定义。

### 3.9 状态连续性与持久化
- 页面切换、刷新、切后台、系统挂起、断网、进程被杀、设备重启后，状态按规则保持或重置。
- 编辑草稿是否丢失；是否提示未保存更改。
- 多窗口/多标签/多设备的状态是否冲突或同步。
- 缓存、离线数据、服务端状态和 UI 状态是否一致。

### 3.10 可访问性与包容性
- 键盘可操作、焦点可见、焦点顺序合理、读屏名称/角色/状态正确。
- 文本放大/系统字体、缩放、高对比度、色弱、减少动态效果等场景是否可用。
- 目标尺寸、颜色对比、错误提示、字幕/文本替代等按适用规范验证。
- 为需要精确拖拽/手势的动作提供替代方式（若适用标准/平台要求）。

### 3.11 时间、响应与并发
- 防抖/节流/连点、双击、长按、快速切换、请求未完成再次操作。
- 慢响应、超时、网络切换、后台恢复、设备忙碌等环境反馈。
- 多用户同时编辑、同一操作并发、异步事件乱序的冲突提示和结果。
- 用户看到的加载状态必须对应真实状态，不应无故永久 loading。

### 3.12 安全与隐私交互
- 授权弹窗是否说明用途；拒绝、稍后、系统设置后返回等路径是否清晰。
- 密码、个人信息、支付信息、受限内容是否按策略遮蔽。
- 外链、下载、危险操作、广告区域、文件打开等是否明确且不诱导误触。
- UI 隐藏控件不等于权限保护，需在服务端/设备端验证授权。

## 4. 测试方法库及使用选择

| 方法 | 适用问题 | 主要产物 |
|---|---|---|
| 场景法/用户旅程 | 用户目标跨页面/角色/系统 | 任务流用例、断点检查 |
| 认知走查 | 首次使用、复杂菜单、功能发现 | 用户逐步理解/疑惑点 |
| 启发式评估 | 快速检查界面常见可用性问题 | 启发式问题清单 |
| 控件状态/状态转换 | 组件或业务对象存在多个状态 | 状态表、合法/非法转移用例 |
| 决策表/因果图 | 角色、条件、开关、策略组合 | 条件组合测试 |
| 等价类/边界值 | 输入、数值、文件、日期、分页 | 边界与非法输入用例 |
| Pairwise/组合测试 | OS×设备×角色×配置组合爆炸 | 组合覆盖集 |
| 探索式测试/错误推测 | 需求遗漏、未知风险、历史问题 | 探索任务、缺陷证据 |
| 视觉比较 | 设计稿、跨端和版本视觉回归 | 截图差异与人工判定 |
| 可访问性测试 | Web/原生无障碍要求 | 自动扫描+人工测试结果 |
| 契约/API/数据验证 | 后台配置影响 C 端数据 | 契约断言、数据一致性证据 |
| 环境/生命周期测试 | App/小程序/桌面/硬件 | 前后台、挂起、重启、断连场景 |

## 5. 一轮快速覆盖方法

新项目首轮不追求穷举，按以下顺序执行：

1. 盘点产品面、页面/视图、核心任务、角色和设备；形成清单，缺失信息明确标为未知。
2. 标出核心入口、关键操作、不可逆动作、后台管理配置、外部跳转和敏感数据。
3. 每页至少检查：进入/离开、默认/空/加载/错误/无权限/禁用状态（按实际适用）、主要控件的正常/重复/失败/取消/返回行为。
4. 每个复杂控件按“触发—处理中—结果—失败—恢复”生成测试点。
5. 表单检查必填、格式、边界、实时/提交校验、粘贴/自动填充、软键盘遮挡、错误定位和内容保持。
6. 列表检查空/单条/多条、搜索、筛选、排序、分页、选择、批量操作、刷新和并发更新。
7. 弹窗/抽屉/菜单检查开关方式、遮罩、ESC/系统返回、点击外部、层级、焦点、滚动锁定和重复打开。
8. 角色先覆盖最高权限、最小权限、无权限和业务相邻角色；分别验证 UI、路由、API、数据范围和状态限制。
9. 后台管理内容的功能必须至少做一条后台操作到 C 端消费结果的链路验证。
10. 检索项目历史 Bug Pattern Library：定位相关页面/控件/数据/角色/平台及其检测点，核对现有用例的触发条件和 oracle；强覆盖跳过，部分覆盖增强，只有真实缺口才新增最小用例。
11. 按风险确定剩余平台组合；核心路径做实机/真浏览器，低风险组合使用 Pairwise。
12. 输出已覆盖、未覆盖、N/A、OPEN 和风险接受项，不以测试用例数量代替覆盖质量。

## 6. 用例判定规则

每条用例的预期结果应尽量可观察、可重复、可判定。推荐把断言分为：

- 用户界面：文本/状态/位置/焦点/反馈/导航/可操作性。
- 交互结果：控件状态变化、操作是否可取消、是否产生重复动作。
- 业务结果：对象状态、关联数据、权限、持久化结果。
- 系统结果：请求、事件、日志、资源、设备反馈（仅在有必要时）。

预期来源标记：REQ（需求）、STD（标准）、PATTERN（既有产品约定）、HEURISTIC（体验启发）、OPEN（待确认）。

“页面正常”“按钮可用”“展示正确”“操作成功”不是充分的预期结果；需写明哪个元素、什么状态、何种响应/跳转、数据是否变化、错误如何呈现。


## 7. 历史 Bug 知识的用例增强原则

历史 Bug 不应在每轮生成中被机械复制成独立回归用例。主功能用例生成 Skill 应读取项目维护的 Pattern Library 和 Coverage Map：

- Pattern 描述缺陷机制，不等同于测试用例；必须说明检测位置、触发条件和可观察断言。
- Pattern 与当前需求相关时，先检查已有用例是否真正包含相同触发与 oracle。
- 强覆盖：只保留 Bug/Pattern 关联，不新增用例。
- 部分覆盖：增强原用例的步骤或断言，避免创建平行用例。
- 无覆盖且当前功能适用：才新增最小必要测试。
- 不适用或证据不足：跳过或标记待确认。
- 多条历史 Bug 属于同一失效模式时，按 Pattern 聚合，不能按 Bug 数量增加用例。

因此评价交互增强效果时，应看发现的真实缺口、历史模式检出率、重复率和执行成本，而不是生成用例数量。
