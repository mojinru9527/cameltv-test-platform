## 一、业务功能测试

### 1.1 冒烟测试

- **原则**：以业务中某一入参为起点，可以完成接口实现的功能，并可以通过结果进行验证或者其他接口得到验证。

### 1.2 场景测试

- **原则**：从业务逻辑层面考虑，通过几个接口的连续调用，达到状态转变的效果，并通过返回结果或者其他接口得到验证。

## 二、健壮性测试

### 2.1 入参合法覆盖测试

- **原则**：在符合接口文档要求的前提下，通过等价类划分和边界值联合使用，进行入参设置。
- **具体包含**：
  - 参数的取值范围覆盖
    - 如果范围小（例如 10 个以内）建议全量取值覆盖
    - 如果范围大，建议按照等价类划分，然后通过边界值的方法进行取值覆盖
  - 组合配置可选参数合法入参
    - 参数类型是符合接口要求的
    - 参数是符合业务逻辑的，真实存在的
  - 覆盖所有必选参数合法入参
    - 参数是符合业务逻辑的，是真实存在的
    - 参数类型是符合接口要求的

### 2.2 入参非法覆盖测试

- **原则**：在不符合接口文档要求的前提下，通过等价类划分和边界值联合使用，进行入参设置。
- **具体包含**：
  - 业务边界取值覆盖
    - 如果需求规定，某字段长度最大长度，则进行超长度限制取值入参，并希望得到服务器相应的处理结果
    - 如果需求规定，某字段不允许包含特殊字符，则进行特殊字符取值入参，并期望得到服务器相应的处理结果
  - 覆盖所有必选参数非法入参
    - 参数类型非法
    - 参数字段缺少
    - 参数字段值缺少
    - 增加不存在的参数
    - 参数设置为特殊字符
    - 参数设置为 -1、0、null

## 三、安全测试

### 3.1 敏感信息是否加密

- 是否使用 https，保证通信过程加密
- 是否包含请求签名，防止参数被篡改
- 是否包含身份确认机制，防止恶意获取他人信息
- 确认 APP、小程序等是否使用 SSL pinning，防抓包机制
- 所有的请求和响应都进行加密操作

### 3.2 SQL 注入

**注意事项**：

- 永远不要信任用户的输入，对用户的输入进行校验，可以通过正则表达式，或限制长度：对单引号和双引号进行转换等
- 永远不要使用动态拼装 sql，可以使用参数化的 sql 或者直接使用存储过程进行数据查询存取
- 永远不要使用管理员权限的数据库链接，为每个应用使用单独的权限有限的数据库连接
- 不要把机密信息直接存放，加密或者 hash 掉密码和敏感的信息
- 应用的异常信息应该给出尽可能少的提示，最好使用自定义的错误信息对原始错误信息进行包装

### 3.3 XSS 攻击：暂不进行

- **原理**：XSS-跨站脚本攻击是指恶意攻击者往 Web 页面里插入恶意 Script 代码，当用户浏览该页之时，嵌入其中 Web 里面的 Script 代码会被执行，从而达到恶意攻击用户的目的。
- **具体内容**：
  - 反射型 XSS：非存储型，就是通过 get 或者 post 请求时，被后端处理过数据，并且响应到前端页面
  - 检测 js 属性函数是否被执行：`<script>alert('xss')</script>`、`document.cookie`
  - 存储型 XSS：XSS 代码被存储到服务器上的数据库里的某张表的字段里，或者页面，或者某个上传文件里
  - 向数据库植入短连接或恶意 xss 语句，页面打开时被执行
  - DOM 型 XSS：仅仅在前端页面进行操作
  - 基于页面元素进行 xss payload：`#'` 相关注入

### 3.4 越权访问

**内容包括**：

- 接口权限最小化
- 每次调用接口将 token 作为 API 参数校验
- 用户相应 API 请求是否合法性
- 是否使用静态 API 密钥，是的话，要强加密后再传输
- 为避免重放攻击，建议参数中包括时间戳和随机数等
- 没有 API 密钥，可以通过访问权限控制

### 3.5 CSRF 请求伪造

- 跨站请求伪造防护：写操作校验来源（Origin/Referer/CSRF Token），防止第三方站点伪造用户请求。

## 四、性能测试（低优先级）

- 性能测试
- 响应时间
- 吞吐量
- 并发数
- 服务器资源使用率
  - CPU
  - IO
  - 内存
  - Network

> 用户指示（2026-08-06）：接口用例中的性能测试优先级放低，作为辅助考虑点（P2/P3）而非阻塞项。

## 五、数据测试

### 5.1 基本测试

- 熟悉数据库字段类型、含义
- 执行操作后，确认数据库正常入库
- 依照需求中要求的某个字段长度、数据类型、长度是否正确定义

### 5.2 专业化

- 数据库表接口是否合理
- 数据结构（如类型、长度）是否正确定义，并需要注意数据结构与输入页面中的数据的长度类型是否一致，如不一致数据库会报错
- 表与表之间的关系是否正确，主外键是否合理
- 索引的创建是否合理
- 存储过程功能是否完整
- 输入能否正确的接收，能否输出正确的结果
- 能否正确插入、更新、删除
- 数据库操作权限定义是否正确
- 能否正确处理并发操作
- 表级、列级完整性约束条件是否满足
- 数据库的处理能力是否满足要求
- 数据库的可靠性、可维护性是否满足要求
- 数据库性能是否满足需求要求
