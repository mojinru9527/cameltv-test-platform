# 生产级模块验收规则

> 本规则由 Batch 47 需求服务的生产级验收方法沉淀而来，适用于其他模块的版本验收与复测。它补充而不替代本目录已有的功能、接口、界面和缺陷规范。

## 1. 适用范围与基本原则

只要结论会被用于“可发布”“生产可用”“验收通过”，就必须执行本规则。模块验收至少覆盖需求、功能/API、权限与租户隔离、事务和数据、浏览器用户旅程、升级迁移、自动化、供应链以及交付证据。

以下原则不可降级：

1. 先固定需求、历史缺陷、代码版本和环境，再设计或执行用例。
2. 需求功能点覆盖率必须为 100%；每个功能点至少有 1 条正面用例和 1 条负面用例。边界、异常、并发或兼容风险存在时，还必须增加对应专项用例。
3. 每条 API 用例必须同时覆盖入参校验、业务逻辑校验和返回值校验；发生写操作时，还必须核对数据库、审计日志和后台任务等副作用。
4. 预期结果必须可观察、可复核。只写“成功”“失败”或“提示正确”不构成有效验收标准。
5. 没有证据不得标记通过；自动化门禁通过不能替代真实浏览器、旧数据库升级或外部关键链路验收。
6. 阻塞和未执行不是通过。外部关键链路缺环境时必须保留为阻塞，并影响最终结论。

## 2. 验收输入与覆盖基线

执行前必须建立以下基线：

| 基线 | 必填内容 | 最低证据 |
| --- | --- | --- |
| 需求基线 | PRD/故事/接口契约、变更范围、明确不在范围内的内容 | 固定版本或可追溯链接 |
| 缺陷基线 | 上一批失败、阻塞、未执行项及历史回归缺陷 | 缺陷 ID、严重程度、状态 |
| 代码基线 | 分支、完整提交 SHA、目标分支 | `git rev-parse HEAD` 输出 |
| 环境基线 | 前后端地址、数据库类型与版本、外部依赖、浏览器/视口 | 脱敏环境清单 |
| 数据基线 | 正常、异常、边界、大数据、跨项目/租户数据 | fixture、初始化脚本或数据说明 |

功能点覆盖矩阵必须在用例设计前完成：

| 功能点 ID | 需求来源 | 主流程 | 备选/异常流 | 正面用例 ID | 负面用例 ID | API/页面入口 | 历史缺陷 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FP-001 | PRD 对应章节 | 描述正常闭环 | 描述拒绝、回滚或降级路径 | TC-MODULE-001 | TC-MODULE-002 | `POST /api/v1/example` / `/example` | 无 |

矩阵中任一功能点缺少正面或负面用例时，覆盖率不合格，不得进入生产放行判定。

## 3. A01–A12 强制门禁

| 编号 | 强制门禁 | 必须验证 | 最低证据 | 阻断条件 |
| --- | --- | --- | --- | --- |
| **A01** | 基线可追溯 | 需求/接口/历史缺陷与用例逐项映射；固定代码 SHA、范围和变更清单 | 覆盖矩阵、版本输出、差异清单 | 功能点、历史失败或版本无法追溯 |
| **A02** | 隔离环境 | 独立 worktree、端口、数据库、配置和测试数据；不污染共享/生产数据 | 环境清单、健康检查、数据库定位信息 | 环境串用、版本不明或数据不可恢复 |
| **A03** | 功能主/备选/异常流 | 每个功能点至少 1 正面 + 1 负面；覆盖主流程、备选流、错误流、边界和状态迁移 | 功能点矩阵、逐条执行结果 | 任一需求点缺覆盖；P0/P1 流程失败或未执行 |
| **A04** | API 三类校验 | 入参、业务逻辑、返回值三类全部验证；写接口核对数据库/审计/任务副作用 | 脱敏请求/响应、DB 查询、日志或任务结果 | 三类校验缺任一项；错误状态码/响应或副作用不一致 |
| **A05** | RBAC 与项目/租户隔离 | 无权限、低权限、跨项目/租户、资源不存在；列表/详情/子资源/写操作均不泄露 | 身份矩阵、请求/响应、无泄露证明 | 越权成功或泄露名称、数量、结构等任何信息 |
| **A06** | UI/API/DB/审计事务一致 | 页面提示、API 返回、业务数据、状态/计数、审计日志同时成功或同时回滚 | UI、响应、事务前后 DB 与审计查询 | 部分提交、数据丢失、假成功/假失败、审计缺失 |
| **A07** | 幂等、并发与重试 | 重复点击、重复请求、并发写入、超时重试和故障恢复 | 并发/重复执行输出、唯一约束和最终 DB 状态 | 重复数据、计数漂移、竞态覆盖或不可恢复中间态 |
| **A08** | 跨页查询一致性 | 数据量超过一页；搜索、筛选、排序、分页、total/count 使用同一条件且顺序稳定 | 大数据 fixture、各页响应、UI 网络与结果 | 第 N+1 页不可达；UI/API/count 结果不一致 |
| **A09** | 浏览器、响应式、a11y 与网络 E2E | 桌面 `1440×900`、平板 `768×1024`、移动 `390×844`；键盘等价操作、焦点、控制台、有效 GET 次数和完整 P0 用户旅程 | 截图/视频、Playwright 结果、控制台与网络记录 | 任一 P0 浏览器/E2E 失败；移动端不可操作；关键操作无键盘等价 |
| **A10** | 真实旧数据库迁移 | 从真实旧版快照升级；数据保留、重复升级、唯一 head、metadata 无漂移；空库不能替代旧库 | 脱敏快照说明、upgrade/current/check 输出、升级前后查询 | 旧库升级失败、丢数据、漂移或仅验证空库 |
| **A11** | 自动化与供应链安全 | 受影响专项、双端全量、类型/构建、行为级测试、依赖/许可证/漏洞审计 | 命令、退出码、通过/失败总数、完整失败集合、审计报告 | 新增回归失败；生产 high/critical 未修复或无批准接受 |
| **A12** | 文档与证据一致 | PRD、OpenAPI、README、ADR、用例、报告、代码事实一致；证据脱敏且可按 ID 定位 | 文档差异、证据索引、缺陷与提交/测试映射 | 结论与证据矛盾；证据缺失/泄密；宣称能力未交付 |

### 3.1 API 三类校验的最低内容

| 类别 | 必测项 |
| --- | --- |
| 入参校验 | 缺失、空/null、类型、长度/值域边界、枚举、默认值、特殊字符、参数组合与跨项目资源 ID |
| 业务逻辑校验 | 正常流程、状态前置、资源不存在、权限/归属、关联接口、重复/并发/重试以及异常回滚 |
| 返回值校验 | HTTP 状态、业务 envelope（如 `code/message/data`）、核心字段、列表数量/排序、错误语义与兼容性 |
| 写操作副作用 | 数据库新增/修改/删除、关联与计数、审计日志、后台任务、文件/缓存；失败时全部不产生或全部回滚 |

## 4. 优先级、状态与发布结论

### 4.1 用例优先级

| 优先级 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 核心路径、数据/安全/升级关键门禁 | 必须执行并通过 |
| P1 | 常用功能、异常流、重要边界 | 必须执行并通过 |
| P2 | 一般功能、兼容、体验或性能风险 | 必须执行；仅可按风险接受流程放行 |
| P3 | 边缘体验或探索项 | 可按风险接受流程处理 |

### 4.2 执行状态

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 实际结果满足全部预期，证据可复核 |
| 失败 | 任一预期不满足，必须关联缺陷 ID |
| 阻塞 | 环境、外部依赖或权限不具备；必须写明解除条件、责任人和预计时间 |
| 未执行 | 尚未执行；生产判定时按风险处理，P0/P1 未执行不得放行 |

### 4.3 客观发布结论

```text
READY
= 所有 P0/P1 通过；
  无致命/严重未关闭问题；
  无影响生产的阻塞或未执行用例；
  A01–A12 均有可复核证据。

CONDITIONAL
= 仅剩已接受的 P2/P3 风险；
  每项风险都有责任人、到期日和明确批准证据；
  不得包含安全隔离、事务一致性、数据丢失、旧库升级或外部关键链路风险。

NEEDS WORK
= 任一 P0/P1 失败；
  或存在跨项目/租户泄露；
  或存在部分提交/数据丢失；
  或真实旧数据库升级失败；
  或存在未接受的 high/critical 漏洞；
  或外部关键流程阻塞；
  或证据不足以证明通过。
```

结论只能从上述条件推导，不能以“单元测试全绿”“构建成功”或“最小链路可用”替代生产验收。

## 5. 证据规范

1. 每条执行用例至少有一种可复核证据；P0 写操作建议同时保留 API、DB/审计和浏览器证据。
2. 证据必须包含用例 ID、代码 SHA、执行日期和环境标识；文件名建议为 `用例ID-证据类型-序号`。
3. 截图、请求/响应、数据库查询、日志和命令输出必须脱敏，不得包含密码、Token、Cookie、私钥、真实个人信息或生产数据。
4. 证据保存在 `work-logs/evidence/批次-模块/`；报告中使用相对链接。临时浏览器状态、数据库文件和原始密钥不得提交。
5. 失败证据必须能同时看出输入、实际结果和预期差异；阻塞证据必须说明缺失条件。
6. 修复复测必须关联历史缺陷、修复提交和自动化测试；只写“已修复”无效。

证据索引模板：

| 用例 ID | 状态 | 证据类型 | 脱敏证据路径/命令 | 代码 SHA | 执行人/日期 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| TC-MODULE-001 | 通过 | 请求/响应 + DB | `work-logs/evidence/batch-module/TC-MODULE-001-api.json` | 完整 SHA | QA / 2026-07-27 | 正常写入且审计同事务提交 |
| TC-MODULE-002 | 失败 | 浏览器 + 日志 | `work-logs/evidence/batch-module/TC-MODULE-002-browser.png` | 完整 SHA | QA / 2026-07-27 | 关联 DEF-MODULE-001 |

### 6.3 阻塞登记模板

| 用例 ID | 缺失条件 | 当前已完成验证 | 解除条件 | 责任人 | 预计时间 | 复测时限 |
| --- | --- | --- | --- | --- | --- | --- |
| TC-MODULE-003 | 真实外部服务或脱敏旧库 | 本地契约、回滚和自动化已通过 | 提供可复核环境、账号/数据并完成真实闭环 | 产品/项目负责人 | 明确日期；未知时写“待确认” | 条件具备后 1 个工作日 |

阻塞项不得只写“环境问题”。责任人和预计时间缺失时，状态仍可记录为阻塞，但 A12 证据门禁判为不通过，最终结论不得高于 `NEEDS WORK`。

## 7. 执行顺序与复测

1. 固定 A01/A02 基线，完成需求与历史缺陷映射。
2. 先执行 P0，再执行 P1、P2、P3；发现致命数据破坏或跨项目泄露时立即停止相关写入并保全证据。
3. 按 A03–A09 完成功能、API、权限、事务、并发、大数据和浏览器用户旅程。
4. 按 A10/A11 完成旧库迁移、全量回归和供应链检查。
5. 按 A12 复核文档、证据和结论，生成 READY、CONDITIONAL 或 NEEDS WORK。
6. 修复后重跑全部历史失败、阻塞和未执行用例，并对受影响主流程做回归；不得只验证缺陷点。
