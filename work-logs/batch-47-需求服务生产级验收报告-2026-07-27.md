# Batch 47 测试平台需求服务生产级验收报告

> 验收日期：2026-07-27

> 隔离后端：`http://127.0.0.1:8006/`

> 执行方式：Codex Agent Team，后端/前端/验收矩阵并行审计，主 Agent 统一复核。

## 1. 验收结论

**结论：不通过（NEEDS WORK），禁止按“生产可交付”放行。**

基础质量门禁全部通过，合法 Markdown 的“上传—列表—删除”最小链路也可用；但生产主链路仍存在以下不可接受问题：

1. 用例批量导入会出现“接口报告失败但数据库已经写入一部分”的数据破坏。
2. 需求模块子节点接口可跨项目读取私有模块名称。
3. 真实生产旧库升级缺必要列迁移；ORM 与 Alembic head 存在全库漂移。
4. AI 用例审查页面和前端调用已存在，但后端审查 API/服务没有交付，浏览器实测 404。
5. 用户在 AI 结果弹窗中的编辑不会随导入保存，系统会静默导入旧内容。
6. 超过 20 MB 的上传返回 HTTP 500，而不是可识别的 413。
7. 同一 AI 用例可重复导入，分类计数和索引状态失真。
8. 上传、拆分、生成、导入、删除等关键写操作的审计日志关闭 Session 后被回滚。
9. 390×844 页面严重裁切，需求模块在移动端基本不可操作。
10. 生产依赖审计仍有 1 个 high、5 个 moderate；全依赖有 2 个 critical、13 个 high。

现状不符合“P0/P1 全过、无严重未关闭缺陷、项目隔离、事务一致、旧库可升级”的生产验收标准。

## 4. 阻断缺陷详述

### B47-DEF-001 导入中途失败仍提交部分用例

| 字段 | 内容 |
| --- | --- |
| 分类 | 功能缺陷 / 数据一致性 |
| 严重程度 | 致命 |
| 优先级 | 最高 |
| 状态 | 新提交 |
| 位置 | `requirement_service.import_cases`、`test_case_service.create_case` |

复现：

1. 准备含 2 条 AI 用例的需求。
2. 让第 1 条创建成功，第 2 条创建抛错。
3. 调用批量导入并查询数据库。

实际：接口返回 `imported=0, skipped=2`，数据库中仍存在第 1 条 TestCase。
预期：整批回滚，TestCase=0，文档状态/计数不变，并返回明确失败。
原因：外层虽声明事务，但单条 `create_case()` 内部执行 `commit()`，破坏原子性。

### B47-DEF-013 子节点 API 跨项目泄露

| 字段 | 内容 |
| --- | --- |
| 分类 | 安全性缺陷 |
| 严重程度 | 致命 |
| 优先级 | 最高 |
| 状态 | 新提交 |
| 位置 | `requirement_modules.get_child_modules` |

复现：以项目 1 用户请求项目 999 的 parent/bundle children。
实际：返回 code 0，并泄露私有节点名 `secret-page`。
预期：403/404，且标题、数量、结构均不可泄露。
原因：只比较 parent 的 release_bundle_id，没有校验当前项目和 bundle 归属，子查询也缺 project_id 条件。

### B47-DEF-019 生产旧库升级缺迁移且 metadata 漂移

| 字段 | 内容 |
| --- | --- |
| 分类 | 配置缺陷 / 数据库升级 |
| 严重程度 | 致命 |
| 优先级 | 最高 |
| 状态 | 新提交 |

模型已使用但 migration 未为旧库补齐：

- `requirement_document.release_bundle_id`
- `requirement_document.linked_swagger_id`
- `requirement_module.description`
- `requirement_module.sort_order`

空库初始迁移调用当前 `Base.metadata.create_all()`，会掩盖旧生产库缺列。`alembic check` 还建议移除 `requirement_review`、性能表、用例分类表等真实对象及 extraction 字段，说明 metadata 注册和迁移契约不一致。
预期：从真实旧版本 PostgreSQL 快照升级到 head 后所有查询可用、数据不丢失、`alembic check` exit 0。

### B47-DEF-005 编辑后的 AI 用例被静默丢弃

| 字段 | 内容 |
| --- | --- |
| 分类 | 功能缺陷 / 数据丢失 |
| 严重程度 | 致命 |

预期：导入用户最终确认的数据，或编辑先持久化并带版本/审查记录。

### B47-DEF-006 重复导入与分类计数失真

### B47-DEF-002 超限文件返回 500

## 6. Batch 46 回归审计

`a68e492` 声称“27 个问题修复 + 15 条测试”，本次复核发现：

- 分页返回结构已修，但页面仍只取前 100 条并做客户端搜索。
- Brief 去掉 content 降低负载，但没有补详情接口，直接破坏正文预览。
- 两条上传大小保护都因异常构造错误返回 500。
- 文件名净化有 helper 测试，但缺 Windows 反斜杠、长度和路由行为边界。
- import 测试只覆盖事务入口前抛错，没有验证真实 commit/rollback。
- `match-api` 请求体已对齐，但没有文档归属校验、确认持久化和追溯关系。
- 模块懒加载性能优化引入孙节点丢失，且没有模块树行为测试。
- 15 条测试中 1 条没有断言；没有 requirement routes/modules、并发、迁移或页面测试。

因此，Batch 46 的“已修复”和历史“需求模块生产可用”结论均不能作为 Batch 47 放行证据。
